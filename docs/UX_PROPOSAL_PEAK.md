# ข้อเสนอ UX — ให้คีย์ง่ายแบบ PEAK (รอลูกพี่ตัดสิน)

ลูกพี่สั่ง 03/11: *"ไม่ใช่ว่าจะเอาให้เหมือน PEAK ทั้งหมด แต่ Logic ในการคีย์จะคล้ายๆกัน
แล้วก็ UX,UI ของเค้าใช้ง่ายผมชอบ ลองดูละกัน แล้ว เรามาว่ากันอีกที"*

เอกสารนี้**ยังไม่ได้ลงมือทำ** เป็นข้อเสนอให้ลูกพี่เลือก ของที่ทำไปแล้วคืนนี้
คือการแก้ของที่**พังหรือปลอม** (ดูท้ายเอกสาร) ไม่ใช่การรื้อ UX

---

## 1. ตอนนี้คีย์หนึ่งรายการต้องทำอะไร

ฟอร์มมี 4 ขั้น

| ขั้น | ถามอะไร |
|---|---|
| 1 | ประเภทรายการ (8 ประเภท) |
| 2 | ผู้ถือกรรมสิทธิ์ (8 ราย) |
| 3 | หมวดย่อย · จำนวนเงิน · วันที่เอกสาร · วันที่เงินเข้า-ออก · บัญชีธนาคาร · ผู้ติดต่อ · ทรัพย์ · ฯลฯ |
| 4 | ยืนยัน (เห็นบรรทัดเดบิต/เครดิตที่จะลง) |

**ค่าใช้จ่ายหนึ่งก้อนที่จ่ายเงินแล้ว** = กดอย่างน้อย 6 ครั้ง และต้องเลือกหมวดย่อย
จาก 16 หมวด ที่ชื่อเป็นศัพท์บัญชี

## 2. PEAK ทำต่างจากเราตรงไหน

ผมเทียบจากโครงการทำงานของ PEAK ที่ผมเข้าถึงได้ (ไม่ได้เปิดหน้าจอจริง —
Claude in Chrome ใช้ไม่ได้ใน session บนคลาวด์ เพราะส่วนขยายอยู่บนเครื่องลูกพี่)

| | PEAK | SRI OS ตอนนี้ |
|---|---|---|
| หน่วยที่ผู้ใช้คิด | **เอกสาร** — ออกใบแจ้งหนี้ · บันทึกค่าใช้จ่าย · รับเงิน | **รายการบัญชี** — ประเภท + หมวดย่อย |
| เริ่มจาก | **ผู้ติดต่อ** เลือกลูกค้า/ผู้ขายก่อน ระบบเติมที่เหลือ | ประเภทรายการ |
| คู่บัญชี | ซ่อนไว้ ระบบเดาจากสินค้า/บริการที่เคยใช้ | ผู้ใช้เลือกหมวดย่อยเอง |
| ค้างรับ-ค้างจ่าย | มีหน้ารวม กดเคลียร์จากที่นั่นได้เลย | ต้องลงรายการใหม่แล้วเลือกหมวดล้าง |
| ของที่ทำบ่อย | ปุ่มสร้างเอกสารเด่น เข้าถึงได้ทุกหน้า | ปุ่ม "บันทึกรายการ" บนแถบบน |

**สิ่งที่ผมคิดว่าควรหยิบมา 3 อย่าง** (เรียงตามคุ้มค่าที่สุด)

### ก. "สิ่งที่ทำบ่อย" บนหน้าแรก — คุ้มที่สุด ทำเร็วที่สุด

ปุ่มใหญ่ 4-6 ปุ่มที่กดครั้งเดียวแล้วฟอร์มเปิดมาพร้อมประเภท+หมวดย่อยที่ถูกแล้ว

> จ่ายค่าส่วนกลาง · รับค่าเช่า · จ่ายค่าน้ำค่าไฟ · โอนเงินระหว่างบัญชี · รับดอกเบี้ย

ตัดจาก 6 กดเหลือ 2-3 กด โดย**ไม่ลดความถูกต้อง** เพราะหมวดย่อยยังถูกเลือกอย่างชัดแจ้ง
แค่ผู้ใช้เลือกผ่านคำพูดที่เข้าใจ ไม่ใช่ผ่านชื่อบัญชี

ลูกพี่ต้องบอกผมว่า **รายการที่ทำบ่อยจริงๆ คืออะไร 5-6 อย่าง** ผมเดาให้ไม่ได้

### ข. หน้า "ค้างรับ-ค้างจ่าย" ที่กดเคลียร์ได้จากที่นั่น

ตอนนี้ถ้าตั้งลูกหนี้ไว้ แล้ววันหนึ่งได้เงิน ต้องจำได้ว่าต้องลงรายการใหม่หมวดไหน
PEAK ให้เห็นรายการค้างทั้งหมดแล้วกด "รับเงิน" ตรงบรรทัดนั้น

อันนี้แก้ปัญหาจริงที่ผมเจอคืนนี้ด้วย — ดูข้อ 4 ข้างล่าง

### ค. คำศัพท์ — เปลี่ยนคำที่ผู้ใช้เห็น ไม่เปลี่ยนคำในโค้ด

ผู้ใช้มีผู้สูงอายุ 3 คน (สุธี · สุดจิตต์ · เบ็ญจพร) คำที่ควรเปลี่ยน เช่น

| ตอนนี้ | เสนอ |
|---|---|
| หมวดย่อย | รายการนี้คืออะไร |
| ผู้ถือกรรมสิทธิ์ | ทรัพย์/เงินนี้อยู่ในชื่อใคร |
| ยังไม่ได้รับ/จ่ายเงิน | ยังไม่ได้รับเงิน / ยังไม่ได้จ่ายเงิน |
| ลักษณะรายการข้ามผู้ถือ | เงินก้อนนี้ระหว่างกันแบบไหน |

**สิ่งที่ผมไม่เสนอให้ทำ** — ซ่อนคู่บัญชีแล้วให้ระบบเดาแบบ PEAK
เพราะคืนนี้ผมเพิ่งแก้บั๊กที่เกิดจากการเดาแบบนั้นพอดี (ข้อ 4)
ระบบนี้เป็นกองกลางของครอบครัว ตัวเลขผิดเงียบๆ แพงกว่าการกดเพิ่มหนึ่งครั้ง

---

## 3. สิ่งที่ลูกพี่ต้องตัดสิน

1. **รายการที่ทำบ่อย 5-6 อย่างคืออะไร** (จำเป็นสำหรับข้อ ก)
2. เอาข้อ ก · ข · ค ทั้งหมด หรือเลือกบางข้อ
3. คำศัพท์ในตารางข้อ ค เอาตามที่เสนอ หรือลูกพี่อยากใช้คำอื่น
4. ตัวกรองเดือนในแถบบน — คืนนี้ผมเอาออกเพราะมันไม่ได้กรองอะไรจริง
   ถ้าอยากมีของจริง ต้องทำให้ครบทั้งเส้นทาง (ทุกหน้าอ่านค่าเดียวกัน) เป็นงานหนึ่งชิ้น

## 4. ของที่ค้างอยู่และเป็นเรื่องตัวเลข ไม่ใช่เรื่องสวยงาม

### 1220 ลูกหนี้อื่น — ตั้งได้แต่เก็บเงินไม่ได้ (เรื่องด่วนที่สุด)

วัดจากตารางกฎจริง

| บัญชีค้าง | ตั้งค้างได้จาก | ทางล้าง |
|---|---|---|
| 1200 ลูกหนี้ค่าเช่า | 2 หมวด | รับชำระ + ตัดหนี้สูญ ✓ |
| 1210 ดอกเบี้ยค้างรับ | 4 หมวด | รับชำระ + ตัดหนี้สูญ ✓ |
| **1220 ลูกหนี้อื่น** | **22 หมวด** | **ตัดหนี้สูญอย่างเดียว** ✗ |
| 2100 เจ้าหนี้ | 35 หมวด | จ่ายชำระ ✓ |

แปลว่า: ติ๊ก "ยังไม่ได้รับเงิน" ในหมวดใดก็ได้จาก 22 หมวด → ลงลูกหนี้ 1220
วันที่ได้เงินจริง **ไม่มีหมวดสำหรับรับเงิน** เหลือทางเดียวคือ `adj.writeoff_other`
ตัดหนี้สูญ ซึ่งลงเป็น**ขาดทุนใน P&L** ไม่ใช่เงินเข้า

นี่คือบทเรียนข้อ 7 ของ CLAUDE.md ตรงตัว: *เปิดฟีเจอร์ครึ่งเดียวอันตรายกว่าไม่เปิด*

**ทำไมผมยังไม่แก้คืนนี้** — ต้องเพิ่มหมวด "รับชำระลูกหนี้อื่น" เข้าตารางกฎ
ซึ่งต้อง sync ขึ้น DB จริงด้วย ถ้าใส่แค่ในโค้ด ฟอร์มจะโชว์หมวดที่ DB ปฏิเสธ
= เปิดครึ่งเดียวอีกแบบ และผมลง migration ขึ้น DB จริงคืนนี้ไม่ได้ (ดูข้อ 5)

**ระหว่างนี้ลูกพี่เลี่ยงได้** — อย่าติ๊ก "ยังไม่ได้รับเงิน" ถ้ายังไม่มีหมวดเฉพาะ
ให้ลงตอนได้เงินจริงไปก่อน ยอดตั้งต้นที่นำเข้าไม่กระทบ

### ไม่มีปุ่มกลับรายการ

ฟอร์มบอกว่าแก้รายการที่ลงผิดได้ด้วยการกลับรายการ แต่หน้าจอไม่มีปุ่มนั้น
(`src/components/ledger/entry-drawer.tsx`) DB บังคับว่าห้าม DELETE อยู่แล้ว
จึงไม่มีทางแก้รายการที่ลงผิดจากหน้าจอเลย

### /settings/users เชิญคนใหม่ไม่ได้

หน้านี้อ่านจาก `app_users` และทำได้แค่แก้ระดับสิทธิ์ของคนที่มีแถวอยู่แล้ว
ครอบครัว 5 คนจึงยังตั้งสิทธิ์จากหน้าจอไม่ได้

### 1310 · 2310 · 2400 — ไม่อันตราย

ออดิทแจ้งว่าอันตรายเหมือน 1220 **แต่ผมตรวจแล้วไม่จริง** ฟอร์มตั้งค้างที่บัญชีพวกนี้
ไม่ได้เลย (0 หมวด) ยอดที่นำเข้ามาแค่ค้างอยู่ ไม่มีรายการใหม่ไปติดเพิ่ม

## 5. ที่ลงขึ้น DB จริงไม่ได้คืนนี้

สองอย่างค้างเพราะเหตุเดียวกัน

1. migration ของฟีเจอร์ติด tag + ถ่วงน้ำหนัก 60/40 (6 ไฟล์ · 403 KB)
2. หมวด "รับชำระลูกหนี้อื่น" ของข้อ 4

**เหตุ** — เครื่องมือ `apply_migration` ต้องให้ผมพิมพ์ SQL ทั้งก้อนผ่านตัวเอง
403 KB ของกฎเงินที่ต้องถอดความด้วยมือ มีความเสี่ยงพิมพ์ผิดจริง และไม่มีใครตรวจตอนกลางคืน
ส่วน `psql` ต่อตรงไม่ได้เพราะนโยบายเน็ตของ environment ปิด `*.supabase.co`

**ทางออกที่ปลอดภัย** — ตั้ง `SRI_DB_URL` ใน environment (เมนู environment → Edit)
แล้ว `scripts/apply-migrations.sh` ลงทีเดียวครบผ่าน psql
**ห้ามส่ง connection string มาในแชท**
