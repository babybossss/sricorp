## เทียบของเก่ากับของใหม่

### ของเก่า — `docs/PLAN.md` §8 และตาราง `app_users` ที่ขึ้น DB ไปแล้ว

3 ระดับ: `management` · `manager` · `user`

```
User / Manager สร้าง ──► pending ──► Management อนุมัติ ──► Ledger
Management สร้าง ─────► ข้ามขั้น ติ๊ก "เข้า Ledger ทันที" ──► Ledger
```

**Manager ในแผนเดิมอนุมัติไม่ได้เลย** — สร้างได้อย่างเดียว เท่ากับ User
ต่างกันแค่เรื่องการเห็นข้อมูล (Manager เห็น Entity ที่ได้รับมอบ · User เห็นแค่งานตัวเอง)
และการจัดการบอร์ด/มอบหมายงาน

### ของใหม่ — ลูกพี่สั่ง 06/10

4 ระดับ: **Super Admin · Management · Manager · Staff**

| | Super Admin | Management | Manager | Staff |
|---|---|---|---|---|
| สร้างรายการ | ✓ | ✓ | ✓ | ✓ |
| **อนุมัติ Ledger** | ✓ | ✓ ของตัวเอง | ✓ **ของตัวเอง (ใหม่)** | ✗ รอ Manager+ |
| **ยืนยันรับ-จ่ายเงิน (CF)** | ✓ | ✓ | **✗ ต้องให้ Management** | ✗ |
| ตั้งค่าระบบ · ผู้ใช้ · สิทธิ์ | ✓ | ✓ | ✗ | ✗ |
| Void / กลับรายการ · เปิดงวดที่ปิด | ✓ | ✓ | ✗ | ✗ |

### สรุปสิ่งที่เปลี่ยนจริง 4 ข้อ

1. **เพิ่ม Super Admin** ซึ่งเดิมไม่มี
2. **Manager อนุมัติ Ledger ได้เอง** — เดิมอนุมัติไม่ได้เลย นี่คือการเปลี่ยนที่ใหญ่ที่สุด
3. **แยก "ยืนยันรับ-จ่ายเงิน" ออกจาก "อนุมัติ Ledger" เป็นคนละสิทธิ์**
   เดิมรวมอยู่ในก้อนเดียว · การแยกนี้**ถูกและสำคัญ** เพราะมันคือสองเรื่องคนละเรื่อง
   (รับรองว่ารายการถูก กับ รับรองว่าเงินเคลื่อนจริง) และเข้ากันพอดีกับ D-068
4. เปลี่ยนชื่อ `user` → `Staff`

## สองเรื่องที่ต้องพูดให้ชัดก่อน

### 1 · "ทำได้ทุกอย่าง" ไม่ได้แปลว่ายกเว้นกฎบัญชี

Super Admin ทำได้ทุก**การกระทำ** แต่ไม่มีใครในระบบที่ยกเว้นจากกฎเงิน:

| กฎ | Super Admin ข้ามได้ไหม |
|---|---|
| ห้ามลบรายการที่ post แล้ว (แก้ด้วย reverse + ลงใหม่) | **ไม่ได้** บังคับที่ DB trigger |
| เดบิต = เครดิต ต้องเท่ากัน | **ไม่ได้** |
| บรรทัดเงินสดต้องผูกบัญชีธนาคาร | **ไม่ได้** |
| `corporate_strict` ต้องมีหลักฐาน + คู่ค้า | **ไม่ได้** |

เพราะถ้าบัญชีใดบัญชีหนึ่งลบรายการที่ลงแล้วได้ ตัวเลขทั้งระบบก็เชื่อไม่ได้อีกต่อไป
และผู้สอบบัญชีจะถามข้อแรกเลยว่า "มีใครลบย้อนหลังได้บ้าง"

**Rank คุมว่าใครทำอะไรได้ ไม่ได้คุมว่ากฎบัญชีใช้กับใครบ้าง** — กฎใช้กับทุกคนเท่ากัน

### 2 · การแยกหน้าที่ — ลูกพี่ยืนยัน 06/10

**Manager อนุมัติ Ledger ได้เอง แต่ยืนยันการรับ-จ่ายเงินไม่ได้ ต้องให้ Management**

คำตอบนี้แก้ปัญหาที่เกือบเกิดพอดี — ถ้า Manager ทำครบทั้งสามขั้น (คีย์ → อนุมัติ →
ยืนยันเงิน) รายการของบริษัทจะเข้า Ledger โดยไม่มีคนที่สองเห็นเลย

พอกั้นที่ขั้นยืนยันเงิน ได้การแยกหน้าที่ที่ถูกจุด:

```
Manager   คีย์ → อนุมัติเอง    = รายการเข้า Ledger · P&L วิ่ง · ลูกหนี้/เจ้าหนี้ขยับ
Management        ยืนยันเงิน   = เงินเข้าบัญชีจริง · CF วิ่ง · ยอดธนาคารขยับ
```

**ขั้นที่แตะเงินจริงมีคนที่สองเสมอ** ส่วนขั้นที่เป็นการบันทึกภาระ/สิทธิ์ให้ Manager
เดินงานได้เอง ไม่ติดคอขวด — และไม่ต้องผูกกับ Entity Policy ให้ซับซ้อนเพิ่ม

**ข้อควรเตรียม**: การยืนยันเงินทั้งบ้านจะไหลมาที่ Management คนเดียวหรือสองคน
ถ้าวันหนึ่งมีสิบรายการ ต้องยืนยันทีละอันคือภาระจริง → หน้า "ยืนยันรับ-จ่าย"
ต้องกรองตามบัญชีธนาคารและยืนยันเป็นชุดได้ ไม่ใช่ทีละแถวอย่างเดียว

## วิธีสร้างที่รองรับ "เปลี่ยนทีหลังได้" และ "อัพเป็น B ได้"

**นี่คือส่วนที่สำคัญกว่าตัวเลขระดับสิทธิ์**

ตอนนี้ RLS เขียนชื่อ role ลงไปตรงๆ — `fn_is_management()` ถูกเรียกใน **12 จุด**
ใน `20260917000004_rls.sql` แปลว่า:

- เพิ่ม Super Admin → ต้องแก้ทั้ง 12 จุด
- ย้ายสิทธิ์หนึ่งข้อจาก Management ไป Manager → ต้องเขียน migration ใหม่
- โมดูลของทาง B (HR · CRM · Kanban) จะเพิ่มอีกหลายสิบจุด

**เปลี่ยนเป็นถามจากตาราง ไม่ใช่ถามจากชื่อ role**

```sql
roles            (key, label, rank_order)
permissions      (key, label, note)        -- ledger.approve · cash.confirm · txn.void ...
role_permissions (role_key, permission_key)

fn_can('ledger.approve')  -- แทน fn_is_management()
```

ผลที่ได้:

| | ตอนนี้ | หลังเปลี่ยน |
|---|---|---|
| เพิ่มระดับสิทธิ์ใหม่ | migration + แก้ 12 จุด | เพิ่มแถวในตาราง |
| ย้ายสิทธิ์ข้ามระดับ | migration | ติ๊กใน Settings |
| ลูกพี่เปลี่ยนใจทีหลัง | ต้องเรียกผม | ทำเองได้ |

ลูกพี่บอกว่า *"สามารถเปลี่ยนทีหลังได้"* — ถ้าทำแบบนี้ มันเปลี่ยนได้จริงโดยไม่ต้องแก้โค้ด
และเป็นสิ่งเดียวกับที่ `docs/PLAN.md` เคยวางไว้ว่าจะมีตาราง `role_permissions`

**ข้อควรระวัง**: ตาราง permission ต้องไม่กลายเป็นช่องให้ปิดกฎเงิน —
มีได้เฉพาะสิทธิ์ว่า "ใครกดอะไรได้" ห้ามมีคีย์แบบ `invariant.skip` หรือ `evidence.waive`
