# ADR 0003 · ถ่วงน้ำหนัก tag (60/40) — ยอดต่อ project บวกกันได้จริง

- **สถานะ** · ตัดสินแล้ว 27/10 · แทนที่การตัดสินข้อ 4.2 ของ ADR 0002 (ทาง A)
- **สั่งโดย** · ลูกพี่ 26/10: *"Tag ขอให้ flexible เลือกได้ 1 project หรือ weighting 60/40 ได้"*
- **ต่อจาก** · `0002-transaction-tags.md` — schema ของ `tag_kinds` / `tags` /
  `transaction_tags` **ใช้ตามเดิมทุกตัว ไม่แก้** ไฟล์นี้เพิ่มของใหม่ข้างบนมันเท่านั้น

---

## 1. ทำไมเปลี่ยนจากทาง A

ADR 0002 เลือก **ทาง A** (ติดได้หลาย tag · ไม่มีสัดส่วน · ยอมรับว่ายอดซ้อน
แล้วบังคับให้ตัวเลขประกาศตัวเองว่าบวกข้าม tag ไม่ได้) และปฏิเสธ **ทาง C**
(ใส่สัดส่วน) ไว้ที่ข้อ 4.3 ด้วยเหตุผลที่ยังถูกอยู่ทุกข้อ

สองอย่างเปลี่ยนไปหลังจากนั้น

**หนึ่ง · ลูกพี่สั่งทาง C ตรงๆ** ADR 0002 ข้อ 7 เขียนไว้เองว่าจะ
*"ขอให้ลูกพี่ยืนยันทาง A หรือสั่ง B ก่อนเริ่มชิ้นงานที่ 1"* — คำตอบที่ได้คือ C
ซึ่งกว้างกว่าทั้ง A และ B (ติด project เดียว = น้ำหนัก 100% · B คือกรณีเฉพาะของ C)

**สอง · ตอนนี้ยังไม่มีอะไรต้องย้อน** ADR 0002 ข้อ 7 ระบุว่าสิ่งที่ย้อนยากที่สุดคือ
การเปลี่ยนจาก A ไป C เพราะ *"ต้องกลับไปตัดสินใบที่ติดหลาย project ทีละใบด้วยมือ
ซึ่งไม่มีใครทำย้อนหลังได้แม่น"* · **สมุดยังว่าง (0 รายการ ณ 27/10)** จึงไม่มีใบไหน
ต้องตัดสินย้อนหลังเลย ต้นทุนของการเลือก C ตอนนี้เท่ากับศูนย์ และจะแพงขึ้นทุกใบที่ลง
นี่เป็นเหตุผลให้ทำ **ตอนนี้** ไม่ใช่ทำทีหลัง

ADR 0002 ข้อ 4.3 เขียนทางไว้ให้แล้วว่า ถ้าจะทำ C
*"ให้ทำเป็น **ตารางแยก** (`tag_allocations`) + ADR ใหม่ ไม่ใช่เติมคอลัมน์"*
ไฟล์นี้คือ ADR ใหม่นั้น และเดินตามทางนั้นทุกตัวอักษร

## 2. สิ่งที่ C แก้ให้ และสิ่งที่ C ไม่ได้แก้

ปัญหาที่ ADR 0002 ข้อ 4.1 กลัวที่สุด: ใบขาย 10,000,000 ที่ติดสอง project
ถูกนับเต็มจำนวนในทั้งสอง → บวกกันได้ 20,000,000 ขณะที่เงินจริงมี 10,000,000
**งบดุลยังดุลสนิทและ health check ยังผ่าน** เพราะไม่มีตัวเลขในสมุดผิดเลย
ผิดเฉพาะ "วิธีรวม" — ตรงกับที่ลูกพี่สั่งห้ามไว้ว่า *อย่าให้กำไรที่ไม่จริงออกมา*

**C แก้ปัญหานี้ที่ราก** ไม่ใช่ปิดป้ายเตือนไว้ข้างๆ: ถ้า Σ น้ำหนัก = 100% พอดี
ยอดที่ปันส่วนแล้วของทุก project จะบวกกันได้ **เท่ากับยอดในสมุดเป๊ะ** เสมอ
→ รายงาน "กำไรต่อ project" และ "% ของ NAV ต่อ project" ที่ ADR 0002 ข้อ 4.4
สั่งไม่ให้เปิด **เปิดได้** เพราะตัวเศษไม่ซ้อนกันแล้ว

**สิ่งที่ C ไม่ได้แก้ และต้องกันเพิ่ม** — C ย้ายความเสี่ยงไม่ใช่ลบความเสี่ยง

| ความเสี่ยงใหม่ที่ C สร้าง | กันด้วย |
|---|---|
| Σ น้ำหนัก ≠ 100% → ยอดรวมต่อ project ไม่ตรงสมุด | constraint trigger แบบ deferred ที่ชั้น DB (ข้อ 4.1) |
| ปัดเศษแล้วผลรวมเพี้ยน / งบต่อ project ไม่ดุล | **ห้ามปัดตอนปันส่วน** เก็บค่าแม่นตรง ปัดตอนแสดงผลเท่านั้น (ข้อ 4.2) |
| น้ำหนักกลายเป็นตัวเลขที่ผู้ใช้กรอกมั่วได้ | น้ำหนักเป็น **สัดส่วน ไม่ใช่จำนวนเงิน** · ตัวคูณมาจากสมุดเสมอ (ข้อ 3.2) |
| แก้น้ำหนักย้อนหลังแล้วกำไรที่เคยรายงานเปลี่ยนเงียบๆ | append-only + ร่องรอยเหมือนลิงก์ tag (ข้อ 3.3) |
| ใบติด `label` ที่ไม่มีน้ำหนัก ถูกเอาไปรวมกับใบที่มี | **แยกวิวคนละตัว** ชื่อคนละแบบ · `label` ยังเป็น touch (ข้อ 5) |

## 3. Schema

### 3.1 `tag_kinds` — เพิ่มสองคอลัมน์ (กฎเหล็กข้อ 5)

| คอลัมน์ใหม่ | ชนิด | seed |
|---|---|---|
| `requires_allocation` | boolean not null default false | `project` = **true** · `label` = false |
| `allocation_note_th` | text | ประโยคกำกับของชนิดที่ปันส่วน (ใช้แทน `aggregate_note_th` ในวิวที่ปันส่วนแล้ว) |

**ทำไมเป็นคอนฟิก ไม่ใช่เช็คชื่อ `'project'` ในโค้ด** — กฎเหล็กข้อ 5 และเหตุผล
เดียวกับที่ ADR 0002 ไม่ทำ `tag_kinds` เป็น enum: วันหนึ่งถ้าลูกพี่อยากให้ `label`
ปันส่วนด้วย มันคือการแก้แถวคอนฟิก + migration backfill ไม่ใช่การไล่แก้โค้ดหลายที่

`aggregate_note_th` ของ ADR 0002 **ยังอยู่และยังบังคับ** สำหรับชนิดที่ไม่ปันส่วน

### 3.2 `sri_os.tag_allocations` — ตารางแยก ตามที่ ADR 0002 สั่ง

| คอลัมน์ | ชนิด | หมายเหตุ |
|---|---|---|
| `id` | uuid PK | surrogate — ต้องรองรับ "แก้สัดส่วนแล้วเก็บของเก่าไว้" |
| `transaction_tag_id` | uuid not null → `transaction_tags(id)` **on delete restrict** | ผูกกับ **ลิงก์** ไม่ใช่ผูกกับใบ+tag ตรงๆ → ถอด tag แล้วน้ำหนักตามไปด้วยโดยไม่ต้องซิงก์สองที่ |
| `weight` | **numeric(9,6)** not null | สัดส่วน `0 < weight <= 1` · `0.600000` = 60% |
| `allocated_at` · `allocated_by` | timestamptz not null · uuid not null → `app_users` | trigger ตั้งจาก `auth.uid()` ปลอมไม่ได้ |
| `superseded_at` · `superseded_by` · `supersede_reason` | timestamptz · uuid · text | **เงื่อนไขสองทาง** เหมือน `untagged_*` ของ ADR 0002 |

**ห้ามมีคอลัมน์จำนวนเงิน** — guard เดิมของ ADR 0002 ที่ไล่ `information_schema.columns`
ขยายมาครอบตารางนี้ด้วย โดยยอมเฉพาะชื่อ `weight` ชนิด numeric ที่ scale = 6
(ไล่จาก `numeric_scale` ไม่ใช่จากชื่อ) · **จำนวนเงินมาจากสมุดเสมอ ตารางนี้ถือแต่ตัวคูณ**

**Index / constraint**

```
unique index tag_alloc_active_uq on tag_allocations (transaction_tag_id)
                                 where superseded_at is null;   -- หนึ่งลิงก์ = หนึ่งน้ำหนักที่ใช้อยู่
check tag_alloc_weight_range:    weight > 0 and weight <= 1
check tag_alloc_supersede_both:  (superseded_at is not null) = (superseded_by is not null)
                             and (superseded_at is not null) = (supersede_reason is not null
                                                                and btrim(supersede_reason) <> '')
check superseded_at >= allocated_at
```

`weight > 0` — **น้ำหนักศูนย์ไม่มีความหมายและอันตราย**: มันคือการติด tag ไว้แล้วบอกว่า
ไม่เกี่ยว ซึ่งถ้าอยากได้แบบนั้นให้ถอด tag (มีร่องรอยชัดกว่า) · ปล่อยให้มี 0 ได้แปลว่า
มีแถวที่โผล่ในรายการ tag แต่ไม่โผล่ในยอด = คนอ่านจะคิดว่าระบบลืมนับ

### 3.3 แก้น้ำหนักย้อนหลัง = ปิดของเก่า + เปิดของใหม่

ไม่มี UPDATE `weight` (trigger ห้าม) · การแก้คือปิดแถวเดิมด้วย
`superseded_*` แล้ว insert แถวใหม่ **ในธุรกรรมเดียว** ผ่านประตู
`fn_reallocate_tags(p_transaction_id, p_kind, p_weights jsonb, p_reason text)`

เหตุผลเดียวกับกฎเหล็กข้อ 1: กำไรต่อ project ที่เคยรายงานไปแล้วคิดจากน้ำหนักชุดเดิม
ถ้าแก้ทับโดยไม่มีร่องรอย จะไม่มีใครอธิบายได้ว่าทำไมตัวเลขเดือนที่แล้วเปลี่ยน
**`p_reason` บังคับ** (ว่างไม่ได้) เหมือน `untag_reason`

## 4. สองด่านที่ทำให้ตัวเลขตรงสมุดเสมอ

### 4.1 Σ น้ำหนัก = 1 พอดี ต่อ (ใบ × ชนิดที่ปันส่วน)

`trg_assert_tag_allocation_complete` — **constraint trigger · deferrable initially
deferred** (แพทเทิร์นเดียวกับด่าน Money Invariants ที่มีอยู่) ยิงตอน commit
จึงยอมให้ระหว่างธุรกรรมมีสภาพกลางที่ยังไม่ครบ 100%

ตรวจต่อ (`transaction_id`, `tag_kind`) ที่ `tag_kinds.requires_allocation`:

1. ทุกลิงก์ที่ยังใช้อยู่ (`untagged_at is null`) **ต้องมี** น้ำหนักที่ยังใช้อยู่
   → ติด project แล้วไม่ใส่น้ำหนัก = **ปฏิเสธ** ไม่ใช่เดาให้เป็น 100%
   (ข้อมูลไม่ครบต้องปฏิเสธ — บทเรียนข้อ 1 ของ mace-windu)
   **ยกเว้นกรณีเดียว**: ติด project อันเดียวบนใบนั้น → ประตูเติม `1.000000` ให้เอง
   ตอนติด ซึ่งไม่ใช่การเดา เพราะมีคำตอบที่ถูกได้คำตอบเดียว
2. `sum(weight) = 1.000000` **พอดี** (เทียบแบบ exact ไม่มี tolerance —
   `numeric` เป็นทศนิยมแม่นตรง และน้ำหนักเป็นค่าที่คนกรอก ไม่ใช่ผลหาร)
3. ไม่มีน้ำหนักที่ยังใช้อยู่ ผูกกับลิงก์ที่ถูกถอดไปแล้ว (กันแถวกำพร้า)

ข้อความ error ต้องบอก **ยอดที่ขาด/เกิน** และ **รายชื่อ tag พร้อมน้ำหนักปัจจุบัน**
ไม่ใช่แค่ "ไม่ถึง 100%" — คนแก้ต้องรู้ว่าจะไปเติมที่ไหน

### 4.2 **ห้ามปัดเศษตอนปันส่วน** — เก็บค่าแม่นตรงไว้ ปัดตอนแสดงผลเท่านั้น

> แก้ 27/10 · ฉบับร่างแรกของข้อนี้สั่งให้ใช้ "กฎเศษตกที่แถวสุดท้าย" (ปัดรายบรรทัด
> แล้วให้แถวสุดท้ายรับเศษ) **ซึ่งผิด** และทดลองแล้วพังจริง — เก็บไว้เป็นทางที่
> ปฏิเสธพร้อมตัวอย่างค้าน ที่ท้ายข้อนี้ เพื่อไม่ให้มีใครเอากลับมาใช้อีก

**กติกา** ในวิว `v_ledger_allocated`:

```
allocated_debit  = debit  * weight      -- ไม่ปัด
allocated_credit = credit * weight      -- ไม่ปัด
```

ปันส่วน **รายบรรทัดบัญชี** ไม่ใช่รายใบ — ตอบคำถามที่ ADR 0002 ข้อ 4.3 ตั้งไว้ว่า
*"ต้องตัดสินว่าสัดส่วนคิดจากยอดใบหรือต่อบรรทัด"* · รายใบทำไม่ได้เพราะ "ยอดใบ"
ของใบเงินต้น+ดอกเบี้ยไม่มีนิยามเดียว

`numeric` ของ Postgres เป็น **ทศนิยมแม่นตรง ไม่ใช่ floating point** จึงได้สองข้อนี้
**เป๊ะทางคณิตศาสตร์** ไม่ใช่ "ใกล้เคียงพอ" — ไม่ต้องมี tolerance ที่ไหนเลย:

1. **ผลรวมข้าม tag = ยอดในสมุด**
   `Σᵢ (amount × wᵢ) = amount × Σᵢwᵢ = amount × 1 = amount`
   (ด่าน 4.1 เป็นคนรับประกันว่า `Σw = 1` พอดี)
2. **งบของแต่ละ project ยังดุล**
   `Σ_บรรทัดเดบิต (dᵢ × w) = w × Σdᵢ = w × Σcⱼ = Σ_บรรทัดเครดิต (cⱼ × w)`
   เพราะคูณ **น้ำหนักตัวเดียวกันทุกบรรทัดของใบนั้น**

ข้อ 2 คือเหตุผลที่เปิดรายงาน "กำไรต่อ project" ได้ — ถ้าข้อนี้ไม่จริง
งบต่อ project จะไม่ดุลและตัวเลขกำไรไม่มีความหมาย

**scale ของคอลัมน์**: ยอดเป็น `numeric(18,2)` คูณน้ำหนัก `numeric(9,6)` ได้ scale 8
วิวต้องปล่อยให้เป็น `numeric` ไม่ระบุ scale **ห้าม cast กลับเป็น (18,2)**
(cast = ปัด = พังทั้งสองข้อข้างบน)

**ปัดที่ไหน** — ปัดเฉพาะ **ตัวเลขก้อนสุดท้ายที่คนอ่าน** หลังรวมเสร็จแล้ว
ไม่ปัดระหว่างทางที่ไหนเลย · ถ้าหน้าไหนต้องให้ยอดต่อ project ที่ปัดแล้วบวกกันได้
เท่ากับยอดรวมที่ปัดแล้วพอดี ให้ใช้กฎเศษ **ที่ชั้นยอดรวมของหน้านั้น** (ไม่ใช่ที่บรรทัด)
และต้องเขียนกำกับว่ากำลังทำอะไรอยู่

#### ทางที่ปฏิเสธ: ปัดรายบรรทัดแล้วให้แถวสุดท้ายรับเศษ

ดูน่าเชื่อเพราะมันรักษาข้อ 1 ได้จริง (ทดสอบแล้วตรงเป๊ะทุกเคสรวมยอดติดลบ)
**แต่มันทำลายข้อ 2** และทำเงียบๆ โดยสมุดใหญ่ยังดุลสนิท

ตัวอย่างค้าน (รันจริงแล้ว) — ใบที่เดบิต `0.05 + 0.05` เครดิต `0.10` แบ่ง A/B อย่างละ 50%

| วิธี | tag | เดบิต | เครดิต | ผล |
|---|---|---|---|---|
| ปัดรายบรรทัด | A | 0.06 | 0.05 | **ไม่ดุล** |
| ปัดรายบรรทัด | B | 0.04 | 0.05 | **ไม่ดุล** |
| ไม่ปัด | A | 0.050 | 0.050 | ดุล |
| ไม่ปัด | B | 0.050 | 0.050 | ดุล |

สาเหตุ: การปัดเกิด **ต่อบรรทัด** ซึ่งฝั่งเดบิตกับฝั่งเครดิตมีจำนวนบรรทัดและยอด
ต่อบรรทัดไม่เท่ากัน เศษจึงตกคนละขนาดสองฝั่ง · ผลรวมข้าม tag ยังตรงสมุด
(0.06+0.04 = 0.10 และ 0.05+0.05 = 0.10) **จึงไม่มีด่านไหนจับได้**
แล้วงบต่อ project จะไม่ดุลโดยไม่มีใครรู้ว่าทำไม — ตรงกับรูปแบบที่ลูกพี่สั่งห้าม

**เทสต์บังคับ** (ไม่ผ่าน = ไม่ merge) ต้องมีทั้งสองข้อ ไม่ใช่ข้อเดียว:
- `Σ allocated = ledger` **เป๊ะ** · `Σ allocated_debit = Σ allocated_credit` **ต่อ tag เป๊ะ**
- เคส: 1/3·1/3·1/3 · 0.6/0.4 · 0.999999/0.000001 · เจ็ดทาง · ยอด 0.01 ·
  **ยอดติดลบ (ใบกลับรายการ)** · **ใบที่สองฝั่งมีจำนวนบรรทัดไม่เท่ากัน** (ตัวอย่างค้านข้างบน)
  · ใบข้ามผู้ถือสองขา

## 5. สองความหมาย ห้ามปนกัน

ADR 0002 สร้างคำว่า **touch** (ยอดที่แตะ tag นี้ · บวกข้าม tag ไม่ได้)
ไฟล์นี้เพิ่มคำว่า **allocated** (ส่วนแบ่งของ tag นี้ · บวกข้าม tag ได้)

| ชนิด | `requires_allocation` | วิวที่ใช้ | บวกข้าม tag |
|---|---|---|---|
| `project` | true | `v_ledger_allocated` · `v_tag_allocated_totals` | **ได้** |
| `label` | false | `v_ledger_tagged` · `v_tag_touch_totals` (ของ ADR 0002) | **ไม่ได้** |

**ห้ามมีวิวหรือหน้าจอไหนเอาสองอย่างมารวมกัน** — ด่าน
`fn_assert_tag_read_path()` ของ ADR 0002 ขยายให้พังเพิ่มเมื่อ:

- มีวิว/ฟังก์ชันที่อ่าน **ทั้ง** `v_tag_touch_totals` และ `v_tag_allocated_totals`
  ในนิยามเดียวกัน (= กำลังเอา touch มาบวกกับ allocated)
- `v_tag_allocated_totals` มีคอลัมน์ชื่อขึ้นต้นด้วย `touched_`
  หรือ `v_tag_touch_totals` มีคอลัมน์ขึ้นต้นด้วย `allocated_` (ชื่อหลอกกัน)
- ชนิดที่ `requires_allocation` โผล่ใน `v_tag_touch_totals`
  หรือชนิดที่ไม่ปันส่วนโผล่ใน `v_tag_allocated_totals`
- `tag_allocations` มีคอลัมน์ numeric ที่ scale ≠ 6 (= มีคนเติมคอลัมน์จำนวนเงิน)
- ด่านกันตัวเองตาย: ไล่ catalog ไม่เจอวิวของตัวเองครบ → พัง (D-096)

ชื่อคอลัมน์ของวิวที่ปันส่วนแล้ว: `allocated_debit` · `allocated_credit` ·
`allocated_txn_count` · **และมี `weight_sum` มาด้วยในแถวเดียวกัน**
(ถ้า `weight_sum` ของแถวไหนไม่ใช่จำนวนเต็มสวยๆ คนอ่านจะเห็นเองว่าใบถูกแบ่ง)
ยังคง **ไม่มี** คอลัมน์ชื่อ `total` หรือ `amount` เปล่าๆ ตามกติกา ADR 0002

  -- ช่อง 'tag_ids'  (array uuid)              — ของ ADR 0002 · ชนิดที่ไม่ปันส่วน

  --    ส่งช่องที่ไม่รู้จัก → ปฏิเสธทั้งคำขอ (แพทเทิร์นเดิมของประตู)

## 8. ย้อนกลับ

ถอดเฉพาะส่วนปันส่วนแล้วกลับไปเป็นทาง A ของ ADR 0002 ได้:
ลบสองวิว · ลบ `tag_allocations` · คืน `fn_post_entry` (ถอด `tag_weights`) ·
`requires_allocation = false` ทุกแถว — **ลิงก์ tag ไม่หาย** เพราะอยู่คนละตาราง

สิ่งที่ย้อนไม่ได้จริง: **น้ำหนักที่คนกรอกไว้หายถาวร** และใบที่เคยแบ่ง 60/40
จะกลับไปถูกนับเต็มจำนวนในทั้งสอง project เงียบๆ → ก่อนย้อนต้อง dump
`tag_allocations` และต้องรู้ว่ารายงานกำไรต่อ project ที่เคยออกไปจะอธิบายไม่ตรงกับ
ของใหม่ · ถ้าจะย้อน ให้ย้อนตอนที่ยังไม่มีใครใช้รายงานนั้นตัดสินใจอะไร
