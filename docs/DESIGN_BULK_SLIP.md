# ลงรายการเป็นชุดจากสลิป (Bulk slip entry)

ลูกพี่สั่ง 06/10/2026 · สถานะ: **ออกแบบแล้ว ยังไม่เขียนโค้ด** (รอ A3 + C4)

> อัพโหลดสลิปธนาคารหรือภาพ capture หลายรูปทีเดียว → ระบบกรอกให้ →
> ตรวจทานแก้บนหน้าเดียว → ส่งเข้าคิวอนุมัติเป็นชุด

**ขอบเขต: เฉพาะรายรับและรายจ่ายเท่านั้น** (ลูกพี่ล็อกไว้)

---

## 1. ทำไมต้องล็อกไว้แค่รายรับ-รายจ่าย

สลิปธนาคารบอกได้แค่ **เงินออกจากบัญชีไหน ไปเท่าไร เมื่อไร ถึงใคร**
มันไม่บอกเจตนาของรายการ รายการสี่กลุ่มนี้จึงรับจากสลิปไม่ได้:

| กลุ่ม | สลิปขาดอะไร | ถ้าเดาแล้วผิดจะเป็นอย่างไร |
|---|---|---|
| โอนระหว่างบัญชี / ข้ามชื่อ | ลักษณะของรายการ (ทดรอง/กู้กรรมการ/เพิ่มทุน/ปันผล) | ปันผลถูกนับเป็นค่าใช้จ่าย หรือเงินกู้ถูกนับเป็นรายได้ |
| ขายทรัพย์ | ต้นทุนเดิมของทรัพย์ชิ้นนั้น | คำนวณกำไร/ขาดทุนไม่ได้เลย |
| คืนเงินกู้ / รับคืนเงินต้น | สัดส่วนเงินต้นกับดอกเบี้ย | ดอกเบี้ยถูกนับเป็นเงินต้น → รายได้หาย (เคยเกิดจริง D-012) |
| ซื้อหลักทรัพย์ / ทองคำ | ทรัพย์ชิ้นไหนที่ผูก | ไม่มีล็อตให้ตัด FIFO ตอนขาย |

รายการกลุ่มนี้ยังคีย์ที่หน้า Ledger ทีละรายการได้เหมือนเดิม และแนบสลิปได้เหมือนกัน
ต่างกันแค่ "ไม่เข้าทาง bulk" เพราะทาง bulk ไม่มีช่องให้กรอกสิ่งที่มันต้องการ

## 2. หมวดที่เข้าทาง bulk ได้ — อ่านจากตารางกฎ ไม่เขียนรายชื่อในโค้ด

```ts
// src/lib/rules/tx-rules.ts
export function isBulkSlipEligible(sub: SubCategory): boolean
```

หมวดย่อยเข้าทาง bulk ได้เมื่อครบทุกข้อ:

1. เงินเคลื่อนจริง — `cash` เป็น `"in"` หรือ `"out"` (ไม่ใช่หมวดตั้งค้าง)
2. กระทบงบกำไรขาดทุน — `affectsPL(sub)` เป็นจริง
3. `requires` ไม่มีอะไรนอกจาก `contact` — เงื่อนไขอื่นทั้งหมด
   (`transferTarget` · `capitalGain` · `repaymentSplit` · การผูกทรัพย์)
   ต้องการข้อมูลที่สลิปไม่มี

**ห้ามเขียนรายชื่อรหัสหมวดใน bulk** (CLAUDE.md: *ห้ามเช็ครหัสหมวดตรงๆ ในโค้ด*)
เพิ่มหมวดใหม่วันหน้าแล้วมันจะเข้า/ไม่เข้าทาง bulk เองตามคุณสมบัติของมัน
ไม่ต้องกลับมาแก้ไฟล์นี้ และไม่มีทางที่รายชื่อสองที่จะไม่ตรงกัน

มีเทสต์บังคับว่า **ทุกหมวดโอน/ขายทรัพย์/คืนเงินกู้/ซื้อหลักทรัพย์ต้องตกออก**
เพื่อไม่ให้การเพิ่มฟิลด์ในตารางกฎวันหน้าทำให้มันหลุดเข้ามาเงียบๆ

## 3. OCR คืนค่าอะไร และห้ามคืนอะไร

```ts
// src/lib/ocr/provider.ts — adapter ชั้นเดียว เปลี่ยนผู้ให้บริการได้ที่หน้า config
export type SlipReading = {
  amount: number | null;
  docDate: string | null;        // ISO
  bankAccountLast4: string | null;
  direction: "in" | "out" | null;
  counterpartyName: string | null;
  referenceNo: string | null;
  /** ความมั่นใจต่อฟิลด์ — ต่ำกว่าเกณฑ์ ช่องขึ้นว่างและแดง */
  confidence: Record<keyof Omit<SlipReading, "confidence">, number>;
};
```

**กฎข้อเดียวที่สำคัญที่สุดของไฟล์นี้: อ่านไม่ออกต้องคืน `null`**

ไม่ใช่ 0 ไม่ใช่วันนี้ ไม่ใช่ค่าที่ใกล้เคียงที่สุด ช่องนั้นขึ้นว่างและบังคับให้คนกรอก
แถวที่ยังมีช่องว่างส่งไม่ได้

เหตุผล: ค่าที่เดามาผิดแล้ว **ยังผ่านการตรวจทุกชั้นได้** เพราะมันเป็นเลขที่ถูกรูปแบบ
double-entry ยังสมดุล trigger ไม่ฟ้อง คนตรวจทานก็เห็นเลขที่ดูสมเหตุสมผล
เทียบกับช่องว่างแดงที่ไม่มีใครพลาดได้ (บทเรียน mace-windu ข้อ 1 และ ข้อ 3)

**ระบบไม่เดาหมวดย่อยให้ ไม่ว่าในกรณีใด** — ไม่เลือกค่าตั้งต้น ไม่เลือก "ที่น่าจะใช่ที่สุด"
สลิปบอกว่า "จ่าย 8,500 ให้คุณสมชาย" มันไม่รู้ว่าเป็นค่าซ่อมหรือค่านายหน้า
และสองอย่างนี้ไปคนละบรรทัดในงบ

## 4. กันสลิปซ้ำ — สามชั้น

สลิปใบเดียวอัพสองรอบ = ค่าใช้จ่ายถูกนับสองครั้ง นี่คือความเสี่ยงหลักของฟีเจอร์นี้

| ชั้น | กลไก | ข้ามได้ไหม |
|---|---|---|
| 1 | `unique (owner_id, source_ref) where source_ref is not null` — เลขอ้างอิงของสลิป | **ไม่ได้** บังคับที่ DB |
| 2 | sha256 ของไฟล์ เทียบกับที่เคยอัพ | เตือน · ยืนยันแล้วผ่านได้ |
| 3 | มี draft หรือรายการ post แล้ว ที่ `(bank_account_id, doc_date, amount)` ตรงกัน | เตือน · ยืนยันแล้วผ่านได้ |

ชั้น 1 ต้องอยู่ที่ DB ไม่ใช่ที่หน้าจอ เพราะสองคนอัพสลิปใบเดียวกันพร้อมกัน
การเช็กที่หน้าจอจะผ่านทั้งคู่

ชั้น 2–3 เป็นคำเตือนไม่ใช่การปิดกั้น เพราะจ่ายคนเดียวกันยอดเดียวกันวันเดียวกันสองครั้ง
เกิดขึ้นได้จริง (ค่าเช่าสองห้องในตึกเดียวกัน)

## 5. การส่ง

- **หนึ่งแถว = หนึ่ง draft** ผูกกันด้วย `batch_id` เดียว
- แถวผ่าน `buildPosting()` **ตัวเดียวกับที่หน้า Ledger ใช้** ทีละแถว
  ไม่มีเส้นทางลัดสำหรับ bulk — กติกาที่ปิดกั้นการคีย์ทีละรายการ
  จะปิดกั้นทาง bulk เหมือนกันโดยอัตโนมัติ
- **ส่งบางส่วนได้**: 10 แถว ผ่าน 8 → 8 แถวเข้าคิว อีก 2 ค้างหน้าจอพร้อมข้อความจาก engine
  บังคับให้ครบก่อนส่ง จะทำให้คนแก้ 2 แถวที่เหลือด้วยการเดา
- **ไม่ post เอง** (กฎเหล็กข้อ 6) ทุกแถวเป็น draft รอ management อนุมัติ
  การอ่านสลิปคือ automation ฟีเจอร์นี้จึงไม่มีปุ่มลงบัญชีตรง
- `source` = `'slip'` ค่าใหม่ใน enum `txn_source` **แยกจาก `'import'`**
  (`'import'` คือยอดตั้งต้นจาก Excel) — ต้องตอบได้ว่าตัวเลขมาจากไหนตอนตรวจสอบย้อนหลัง

## 6. corporate_strict

`buildPosting()` บังคับสองอย่างกับนิติบุคคล: ไฟล์หลักฐาน + คู่ค้า

- **ไฟล์หลักฐาน**: สลิปคือไฟล์หลักฐานอยู่แล้ว ข้อนี้ผ่านอัตโนมัติ —
  เป็นผลพลอยได้ที่ดีของฟีเจอร์นี้ ไม่ใช่การผ่อนกฎ
- **คู่ค้า**: OCR ให้แค่ชื่อ ไม่ใช่ `contact_id` → แถวของบริษัทต้องจับคู่
  (หรือสร้างใหม่) ก่อนส่ง แถวของบุคคลไม่ต้อง

ระบบเสนอคู่ค้าที่ชื่อใกล้เคียง แต่ **คนกดยืนยัน** — จับคู่ผิดคนแล้วยอดค้างจะไปอยู่ชื่อผิด

## 7. สิ่งที่ต้องเติมในฐานข้อมูล

`draft_entries` วันนี้ยังขาด:

| คอลัมน์ | ทำไมต้องมี |
|---|---|
| `bank_account_id` | Money Invariant 2 บังคับว่าบรรทัดเงินสดต้องผูกบัญชี · ตอนนี้ draft ไม่มีที่เก็บ จึงต้องมีก่อน A3 ไม่ใช่ก่อน C5 |
| `source_ref` | มีแล้ว — ใช้เก็บเลขอ้างอิงสลิป ต้องเพิ่ม unique index |
| `file_sha256` (ที่ตาราง attachment) | กันชั้น 2 |

`batch_id` · `source` · `attachments` มีอยู่แล้วในสคีมาตั้งแต่ต้น ไม่ต้องเพิ่ม

## 8. ลำดับ

ต่อยอดจากสองอย่างที่ยังไม่มี:

1. **A3** — การเขียน draft ลง DB ตอนกดส่ง · bulk คือการเรียกสิ่งนี้ N รอบ
   เขียน bulk ก่อน A3 = เขียนสองรอบ
2. **C4** — Supabase Storage · ไม่มีที่เก็บไฟล์ ก็ไม่มีสลิปให้อ่าน

เพิ่มเข้าแผนเป็น **C5 · 5–8 ชม** (adapter OCR 2 · หน้าตรวจทาน 2–3 · กันซ้ำ 1–2 · เทสต์ 1–2)

ถ้าลูกพี่อยากใช้เร็วกว่านั้น ดึง **C4 + C5 ขึ้นมาทันทีหลัง A3** แล้วเลื่อนงบ PL/CF
(B3) ไปทีหลัง — ได้ใช้เร็วขึ้นประมาณ 4–6 คืน
