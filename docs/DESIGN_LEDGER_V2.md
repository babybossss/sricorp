# งานเพิ่มฝั่ง Ledger — ลูกพี่สั่ง 06/10/2026

ห้าข้อ · สถานะ: **ออกแบบแล้ว ยังไม่เขียนโค้ด** · ข้อ 5 ต้องให้ลูกพี่ตัดสินใจก่อน

## 1 · คิวอนุมัติ — กดแถวแล้วเปิดหน้าต่างตรวจ

กดแถวในคิวอนุมัติ → หน้าต่างขึ้นมาแสดงรายการเต็มโดยไม่ต้องออกจากคิว

ในหน้าต่างต้องมี: หัวรายการ (ผู้ถือ · ประเภท · หมวดย่อย · วันที่ · จำนวนเงิน) ·
**บรรทัดบัญชีสองด้านที่จะลงจริง** · ไฟล์แนบเปิดดูได้ · คู่ค้า · ทรัพย์ที่ผูก ·
โครงการ · ใครเป็นคนคีย์เมื่อไร · ปุ่มอนุมัติ/ตีกลับพร้อมช่องเหตุผล

**บรรทัดบัญชีต้องมาจาก `previewPosting()` เท่านั้น** ห้ามให้หน้าต่างคำนวณคู่บัญชีเอง
(บทเรียน mace-windu ข้อ 5: กฎเดียวกันเขียนสองที่ แล้วสิ่งที่คนอนุมัติเห็น
กับสิ่งที่ลงจริงจะแยกจากกันได้ — ซึ่งแปลว่าการอนุมัติไม่มีความหมาย)

ปุ่มถัดไป/ก่อนหน้าในหน้าต่าง เพื่อไล่ตรวจทั้งคิวได้โดยไม่ต้องปิดเปิด

## 2 · Project — มิติใหม่บนทุกรายการ

ช่อง `project` เป็น dropdown ตั้งค่าได้ใน Settings ใช้แยกคำนวณผลตามโครงการ

### ตาราง

```
projects (id, code, name, status active/closed, started_on, closed_on, note)
transactions.project_id uuid null references projects(id)
draft_entries.project_id uuid null references projects(id)
```

### กฎที่ต้องบังคับ

| กฎ | เหตุผล |
|---|---|
| **โครงการไม่แตะคู่บัญชีเลย** — เป็นมิติสำหรับจัดกลุ่ม ไม่ใช่บัญชี | ถ้าโครงการไปเปลี่ยน dr/cr ได้เมื่อไร ตารางกฎจะไม่ใช่แหล่งความจริงเดียวอีกต่อไป |
| **ไม่บังคับกรอก** | รายการเก่าทั้งหมดไม่มีโครงการ บังคับเมื่อไรคือทำให้ของเดิมผิดทันที · ถ้าจะบังคับ ให้บังคับผ่าน Entity Policy ทีหลัง |
| **โอนข้ามผู้ถือ สองขาต้องโครงการเดียวกัน** | สองขาคือรายการเดียวกัน ถ้าแยกโครงการได้ ยอดโครงการจะไม่ปิด |
| **ปิดโครงการแล้วเลือกใหม่ไม่ได้ แต่รายการเก่ายังอยู่** | ไม่งั้นต้องลบประวัติเพื่อปิดโครงการ ซึ่งชนกฎเหล็กข้อ 1 |
| รายงานทุกหน้าที่กรอง Entity ได้ **ต้องกรองโครงการได้ด้วย** | ไม่งั้นมีมิติที่ดูได้แค่บางหน้า |

### ที่ตั้งใจไม่ทำ

**หนึ่งรายการ = หนึ่งโครงการ** ไม่แบ่งสัดส่วนข้ามโครงการในรายการเดียว

ซื้อของใช้สองโครงการ → คีย์สองรายการ แบ่งยอดเอง เหตุผล: การแบ่งสัดส่วนต้องมีกฎว่า
แบ่งอย่างไร แบ่งแล้วใครตรวจ และปัดเศษไปทางไหน — สามข้อนั้นทำครึ่งเดียวแล้วยอดจะไม่ลงตัว
ถ้าวันหน้าจำเป็นจริง ค่อยเพิ่มที่ระดับ `transaction_lines` ไม่ใช่ที่ระดับรายการ

## 3+4 · Auto-Key จากทะเบียนทรัพย์

### ที่มีอยู่แล้ว

`assets.status` มี `active` / `inactive` / `sold` / `redeemed` อยู่ในสคีมาแล้ว
`schedules` ก็มี แต่ผูกกับ `contracts` ไม่ใช่กับทรัพย์ และเป็นตารางงวดคงที่ ไม่ใช่รายการประจำ

### ที่ต้องเพิ่ม

```
asset_recurring (
  id, asset_id, txn_type_code,        -- หมวดย่อยจากตารางกฎ
  direction income/expense,
  amount, frequency monthly/quarterly/semiannual/annual,
  day_of_month, start_date, end_date null,
  contact_id null, project_id null,
  bank_account_id null,               -- บัญชีที่คาดว่าเงินจะเข้า/ออก
  is_active boolean
)
asset_recurring_runs (plan_id, period_key, draft_entry_id, unique(plan_id, period_key))
```

ตัวอย่างที่ลูกพี่ยกมา: ค่าเช่ารายเดือน (รายได้) · ค่าล้างแอร์ราย 3 เดือน (ค่าใช้จ่าย) ·
ค่าส่วนกลางรายปี (ค่าใช้จ่าย)

### รอบการทำงาน

```
cron รายวัน
  → หาแผนที่ถึงกำหนดในอีก N วัน
  → ข้ามแผนที่ทรัพย์ status ไม่ใช่ active
  → ข้ามแผนที่งวดนี้สร้างไปแล้ว (unique)
  → สร้าง draft ผูก batch_id เดียวกัน source = 'schedule'
  → Management Team เปิดดูเป็นชุด ตรวจ แล้วอนุมัติทีเดียว
```

### กฎที่ต้องบังคับ

| กฎ | ถ้าไม่มีจะเกิดอะไร |
|---|---|
| **ทรัพย์ไม่ active → ไม่สร้าง draft** | ห้องว่างไม่มีคนเช่าจะมีรายได้ค่าเช่าเกิดขึ้นทุกเดือน = รายได้ปลอม |
| `unique (plan_id, period_key)` | cron รันซ้ำ/รันสองเครื่อง = ค่าเช่าเดือนเดียวถูกบันทึกสองรอบ |
| **แก้ยอดในแผน ไม่ย้อนไปแก้ draft ที่สร้างแล้ว** | ขึ้นค่าเช่าแล้วยอดเดือนที่อนุมัติไปแล้วเปลี่ยนตาม = ประวัติเพี้ยน |
| **สร้างได้แค่ draft ห้าม post** (กฎเหล็กข้อ 6) | — |
| ทรัพย์เปลี่ยนเป็น inactive กลางคัน → หยุดงวดถัดไป ไม่ลบงวดที่ออกไปแล้ว | งวดที่ออกแล้วอาจอนุมัติไปแล้ว ลบไม่ได้ (กฎเหล็กข้อ 1) |

### หน้าจอ

- **ทะเบียนทรัพย์**: แท็บ "รายการประจำ" ต่อทรัพย์หนึ่งชิ้น เพิ่ม/แก้/ปิดแผนได้
  พร้อมบรรทัดสรุป "ทรัพย์ชิ้นนี้คาดว่ารายได้ปีละเท่าไร ค่าใช้จ่ายปีละเท่าไร"
- **คิวอนุมัติ**: จัดกลุ่มตาม `batch_id` กดอนุมัติทั้งชุดได้ แต่**กางดูทีละแถวได้เสมอ**
  (ข้อ 1) เพราะ bulk approve ที่กางดูไม่ได้ก็คือการอนุมัติโดยไม่ได้ตรวจ

## 5 · งบกระแสเงินสดต้องไม่วิ่งจนกว่าจะ check ว่าเงินเข้า/ออกจริง

**นี่คือข้อที่กระทบโครงสร้าง ต้องให้ลูกพี่เลือกก่อนลงมือ**

### สิ่งที่ลูกพี่ต้องการ

คีย์แล้ว อนุมัติแล้ว ก็ยังไม่พอ — ต้องมีคนยืนยันว่าเงินเข้าจริง/ออกจริง และระบุว่า
เข้าบัญชีไหน ออกจากบัญชีไหน · งบกระแสเงินสดนับเฉพาะรายการที่ยืนยันแล้ว

สิ่งนี้คือการแยกหน้าที่: คนคีย์บันทึกภาระ/สิทธิ์ คนดูบัญชีธนาคารยืนยันเงิน

### ที่มีอยู่แล้วในสคีมา

- `transactions.cash_date` — คอมเมนต์ในไฟล์ migration เขียนไว้ตรงๆ ว่า
  *doc_date เข้า P&L (accrual) · cash_date เข้า CF · null = ยังค้างรับ/ค้างจ่าย*
- `cash_confirmations` — มี `bank_account_id` · `actual_amount` · `actual_date` ·
  `is_partial` · `confirmed_by` ครบแล้ว
- `PostingInput.notYetPaid` ใน engine → ส่งไปลงลูกหนี้/เจ้าหนี้แทนเงินสด

แปลว่าโครงมีอยู่แล้ว **สิ่งที่ขาดคือการบังคับ และหน้าจอยืนยัน**

### วิธีที่ถูก และวิธีที่ดูเหมือนถูกแต่ผิด

**วิธีที่ผิด**: ลงเงินสดตามปกติ แล้วติดธง `cash_confirmed = false` ให้รายงาน CF กรองออก

ผิดสองชั้น:
1. **งบดุลจะโกหก** — ยอดเงินในบัญชีธนาคารจะมีเงินที่ยังไม่เข้าจริง
   กระทบยอดกับ statement ไม่ได้ (Money Invariant 5)
2. **งบดุลกับงบกระแสเงินสดจะไม่ตรงกัน** — BS บอกว่าเงินเข้าแล้ว CF บอกว่ายังไม่เข้า
   สองงบที่ต้องกระทบกันได้ กลับขัดกันเอง
3. ธงเป็นสิ่งที่**รายงานต้องจำว่าต้องกรอง** — รายงานหน้าถัดไปที่ใครเขียนวันหน้าแล้วลืมกรอง
   จะนับเงินที่ยังไม่เข้าทันที โดยไม่มีอะไรฟ้อง

**วิธีที่ถูก**: ยังไม่ยืนยัน = **ไม่มีบรรทัดเงินสดเลย** เงินไปพักในบัญชีพัก

```
ตอนอนุมัติ     ค่าเช่าเดือน ต.ค.    Dr ลูกหนี้ค่าเช่า 1200 / Cr รายได้ค่าเช่า 4200
                                     → P&L วิ่ง · CF ไม่วิ่ง · ธนาคารไม่ขยับ

ตอน check      เงินเข้า SCB จริง    Dr เงินฝากธนาคาร 1100 / Cr ลูกหนี้ค่าเช่า 1200
                                     → CF วิ่งตอนนี้ · ธนาคารขยับตอนนี้
```

CF ไม่ต้องกรองอะไรเลย เพราะ**ไม่มีบรรทัดเงินสดให้นับตั้งแต่แรก** — กันไม่ให้ผิดได้
ด้วยโครงสร้าง ไม่ใช่ด้วยการที่ทุกคนต้องจำกฎ

และ `cash_date` **ต้องตั้งโดย trigger ตอนยืนยันเท่านั้น** แก้มือไม่ได้ ไม่งั้นมันกับ
`cash_confirmations` จะไม่ตรงกันเงียบๆ

### ปัญหาที่ต้องแก้ก่อน — บัญชีพักยังไม่ครบทุกหมวด

หมวดย่อยที่เงินเคลื่อนจริงมี **53 หมวด** แต่ตั้งบัญชีพักไว้แล้วแค่ **21 หมวด**
(ค่าเช่า ดอกเบี้ยรับ และค่าใช้จ่ายทั้งหมด) อีก **32 หมวดยังไม่มี**

ถ้าเปิดกฎโดยที่หมวดพวกนี้ไม่มีที่พัก มันจะตกไปเส้นทางเดิมคือลงเงินสดตรง
= **เปิดกฎครึ่งเดียว** ซึ่งอันตรายกว่าไม่เปิด (บทเรียนข้อ 7)

**ไม่ต้องสร้างกลไกใหม่ — ใช้ลูกหนี้กับเจ้าหนี้เหมือนเดิมทุกหมวด**

| ทิศทาง | พักที่ | ความหมายที่อ่านออกในงบ |
|---|---|---|
| เงินกำลังจะเข้า | **ลูกหนี้** | คนอื่นยังไม่จ่ายเรา |
| เงินกำลังจะออก | **เจ้าหนี้** | เรายังไม่จ่ายเขา |

เคยคิดจะตั้งบัญชี "เงินระหว่างทาง" แยกต่างหากสำหรับหมวดลงทุน/การเงิน
เพราะมองว่ามันไม่ใช่ลูกหนี้-เจ้าหนี้ตามปกติ — **คิดผิด** ลองไล่ดูทีละตัวแล้วมันเป็น
ลูกหนี้-เจ้าหนี้จริงๆ ทุกตัว และเป็นการลงบัญชีที่ถูกต้องกว่าด้วย:

```
ขายทองคำ 500,000 (ต้นทุน 400,000)
  อนุมัติ   Dr ลูกหนี้อื่น      500,000
            Cr ทองคำ                      400,000
            Cr กำไรจากการขายทรัพย์         100,000
            → P&L วิ่ง (กำไร 100,000) · CF ไม่วิ่ง · ธนาคารไม่ขยับ
  check     Dr เงินฝาก SCB      500,000
            Cr ลูกหนี้อื่น                 500,000
            → CF +500,000 (Investing)

ชำระคืนเงินกู้ธนาคาร 1,000,000
  อนุมัติ   Dr เงินกู้ธนาคาร  1,000,000
            Cr เจ้าหนี้                  1,000,000
            → หนี้สินรวมเท่าเดิม แค่ย้ายจาก "เงินกู้" ไป "ที่ต้องจ่ายทันที"
  check     Dr เจ้าหนี้        1,000,000
            Cr เงินฝาก                   1,000,000
            → CF −1,000,000 (Financing)
```

ตัวที่สองแสดงให้เห็นว่าทำไมวิธีนี้ปลอดภัย: **งบดุลยังพูดความจริงตลอดเวลา**
หนี้สินรวมไม่เปลี่ยน เพราะเรายังไม่ได้จ่ายอะไรออกไปจริง

### ที่ต้องเพิ่มจริงๆ มีบัญชีเดียว

ผังบัญชีมีลูกหนี้แค่สองตัวที่เจาะจง (1200 ค่าเช่า · 1210 ดอกเบี้ย)
ส่วนฝั่งเจ้าหนี้มี 2100 เจ้าหนี้การค้า-เจ้าหนี้อื่น ซึ่งกว้างพออยู่แล้ว

เพิ่ม **`1220 ลูกหนี้อื่น (รอรับเงิน)`** ตัวเดียว แล้วเติม `accrualCoa` ให้ครบ 53 หมวด:

- เงินเข้าที่ไม่ใช่ค่าเช่า/ดอกเบี้ย (ปันผล · เงินกินเปล่า · ค่าธรรมเนียม · ขายทรัพย์ ·
  ไถ่ถอน · รับคืนเงินกู้ · กู้เงินเข้า · เพิ่มทุน · มัดจำรับ) → **1220**
- เงินออกทั้งหมด (ซื้อทรัพย์ · ปล่อยกู้ · คืนเงินกู้ · ดอกเบี้ยจ่าย · ถอนทุน ·
  คืนมัดจำ) → **2100**

### จุดที่ต้องระวัง — ล้างลูกหนี้ซ้ำสองทาง

ตารางกฎมีสามหมวดที่ตัวมันเองคือการล้างลูกหนี้/เจ้าหนี้อยู่แล้ว:
`inv.collect_rent` · `inv.collect_interest` · `fin.pay_payable`

พอการ check สร้างบรรทัดล้างให้อัตโนมัติ **จะมีสองทางที่ล้างลูกหนี้ตัวเดียวกันได้**
ถ้าใครคีย์ "รับชำระค่าเช่าค้างรับ" ทั้งที่รายการเดิมก็รอ check อยู่ ลูกหนี้จะถูกล้างสองรอบ
แล้วติดลบ

**ทางออก**: เก็บสามหมวดนี้ไว้ แต่จำกัดให้ใช้กับ**ลูกหนี้/เจ้าหนี้ที่มาจากยอดตั้งต้น**
(import จาก Excel) เท่านั้น ซึ่งไม่มีรายการต้นทางให้ check · ลูกหนี้ที่เกิดจากรายการในระบบ
ต้องล้างผ่านการ check ทางเดียว

### คำถามที่ต้องให้ลูกพี่ตอบ

**ถ้าคนคีย์ถือสลิปอยู่ในมือ (เห็นกับตาว่าเงินออกไปแล้ว) ยังต้องให้คนอื่นมา check อีกไหม**

| ตัวเลือก | ผล |
|---|---|
| **ก · ต้อง check ทุกรายการเสมอ** | เข้มที่สุด แยกหน้าที่จริง · แต่ทุกรายการมีสองขั้นตอน แม้แต่รายการที่เห็นสลิปแล้ว |
| **ข · คนคีย์ติ๊ก "เงินเข้าแล้ว" พร้อมเลือกบัญชี = ยืนยันในตัว** | เร็วกว่ามาก · แต่ไม่มีการแยกหน้าที่ คนคีย์ยืนยันตัวเอง |
| **ค · ฝั่งบริษัทต้อง check เสมอ ฝั่งบุคคลติ๊กเองได้** | ตรงกับ Entity Policy ที่ใช้อยู่ — บริษัทเข้ม บุคคลยืดหยุ่น |

**ผมแนะ ค** เพราะเป็นกฎเดียวกับที่ระบบใช้อยู่แล้วทุกเรื่อง ไม่ต้องจำกฎใหม่
