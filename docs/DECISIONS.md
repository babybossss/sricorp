### D-011 · พิสูจน์แล้วว่า Money Invariants กันได้จริงที่ระดับ DB
ไม่ได้เชื่อว่าเขียน trigger แล้วจะทำงาน — ลองละเมิดจริงทีละข้อ

| ทดสอบ | ผล |
|---|---|
| รายการไม่สมดุล (Dr 12,000 / Cr 9,999) | ✅ ถูกปฏิเสธ + rollback ทั้งชุด |
| บรรทัดเงินสดไม่ผูกบัญชีธนาคาร | ✅ ถูกปฏิเสธ |
| รายการที่ถูกต้อง | ✅ บันทึกได้ตามปกติ |
| ลบรายการที่บันทึกแล้ว | ✅ ถูกปฏิเสธ ให้ใช้ reverse |
| Corporate ไม่แนบหลักฐาน | ✅ ถูกปฏิเสธ |
| Corporate แนบหลักฐานแล้ว | ✅ บันทึกได้ |

**หมายเหตุทางเทคนิค**: trigger ตรวจสมดุลเป็น `deferrable initially deferred`
คือ fire ตอน **COMMIT** ไม่ใช่ตอน INSERT — จำเป็น เพราะระหว่างใส่บรรทัดแรก
รายการยังไม่สมดุลโดยธรรมชาติ ผลคือ application จะรู้ว่าผิดตอน commit
ซึ่งถูกต้องแล้ว (ทั้งรายการเข้าหรือไม่เข้าเลย ไม่มีครึ่งๆ กลางๆ)

การทดสอบรอบแรกรายงานผิดว่าข้อ 1 ไม่ผ่าน เพราะสคริปต์ลบข้อมูลทิ้งก่อน commit
จึงไม่ทัน trigger — ทดสอบซ้ำแบบปล่อยให้ commit จริงแล้วยืนยันว่ากันได้

### D-021 · เรียก mace-windu ตรวจจริงตามกติกาข้อ 7 — **BLOCK สองรอบ**
นี่คือครั้งแรกที่ใช้สภาเจไดจริง ไม่ใช่แค่มีไฟล์ และมันจับของได้

**รอบแรก — 8 ข้อ (7 ข้อถูกต้อง)**

ที่ร้ายที่สุดสองข้อ ทั้งคู่เป็น**การลงบัญชีผิดแบบเงียบๆ**:
- เลือกหมวด "คืนเงินกู้" แต่ไม่กรอกการแยกเงินต้น/ดอกเบี้ย → โค้ดตกไปเส้นทางปกติ
  ลงเงินต้นเต็มจำนวน **ดอกเบี้ยหายจาก P&L และหนี้สินลดเกินจริง**
- ขายทรัพย์โดยไม่กรอกต้นทุน → ตัดทรัพย์ด้วย**ราคาขาย**แทนต้นทุน ไม่รับรู้กำไรเลย

อีกข้อที่มีผลจริง: hard-code 4300/5900/5400 ไว้ใน engine ทำให้**กำไรจากการขายหลักทรัพย์
ไปโผล่บรรทัด "กำไรจากการขายทรัพย์"** ซึ่งหมายถึงอสังหาฯ — ย้ายเข้าตารางกฎเป็น
`gainCoa` / `lossCoa` / `interestCoa` แล้วแยก `inv.sell_securities` ไปใช้ 4900

ข้อที่ไม่ทำตาม: เสนอให้ใส่ `ownerId` ในบรรทัดบัญชี — แต่ `transaction_lines`
ไม่มีคอลัมน์นั้น owner อยู่ที่ระดับ transaction ตอบกลับไปแล้วและ mace-windu เห็นด้วย

**รอบสอง — 6 ข้อ (ทุกข้อถูกต้อง)**

ข้อที่ลึกที่สุดคือผลพวงจากคำตอบข้างบน: **ถ้า 1 transaction = 1 owner
แปลว่าโอนข้ามผู้ถือเป็นสองบรรทัดเงินสดในรายการเดียวไม่ได้** เพราะเงินสดของอีกฝ่าย
จะไปโผล่ในงบของฝ่ายแรก และ `intercompanyNature` เดิมอยู่แค่ใน summary ไม่ได้ลงบัญชีเลย
→ เคสปันผลจาก SRI ให้ธนากร **ไม่ลดส่วนของเจ้าของ** ผิดกฎที่เขียนไว้เองใน LEDGER_RULES

แก้เป็น: คืน **สอง transaction คู่กัน** ฝ่ายละหนึ่ง แต่ละอันสมดุลในตัวเอง
พร้อมคู่บัญชีตามลักษณะ — ปันผล: ฝ่ายจ่าย Dr 3200 (ลดส่วนของเจ้าของ) · ฝ่ายรับ Cr 4410 (รายได้)

อีกข้อที่สำคัญ: **อย่าเชื่อฟิลด์ที่ผู้ใช้เว้นได้** — เดิมดูว่าข้ามผู้ถือจาก
`transferToOwnerId` ที่เป็น optional ไม่ส่งมาก็ถือว่าโอนภายใน ทั้งที่บัญชีปลายทาง
เป็นของคนอื่น ตอนนี้อ่านจาก `BANKS` เอง

แปลว่า **สิ่งที่ผู้ใช้เห็นก่อนกดยืนยัน กับสิ่งที่ระบบบันทึกจริง แยกจากกันได้ทุกเมื่อ**

  `isBalanced` ทิ้ง · `posting.ts` เรียก `computeDisposal()` ต่อแทนคำนวณซ้ำ
- เพิ่ม `lib/ledger/preview.ts` ให้ฟอร์มเรียก engine ตัวจริงมาแสดง
- เทสต์ที่เคยยิงใส่ `disposalJournal()` ย้ายไปยิงผ่าน `buildPosting()` —
  ของเดิมพิสูจน์ฟังก์ชันที่ไม่มีใครเรียกจริง

### D-025 · แยก `buildPostingDraft()` ออกจาก `buildPosting()`
ปัญหา: พรีวิวต้องแสดงบรรทัดได้ตั้งแต่ยังไม่แนบไฟล์ แต่ `corporate_strict`
บังคับว่าต้องมีไฟล์หลักฐาน ถ้าใช้ฟังก์ชันเดียวกัน นิติบุคคลจะเห็นแต่
"ต้องแนบหลักฐาน" ไม่มีวันเห็นคู่บัญชีเลย

ทางที่ **ไม่เลือก**: ใส่ flag แบบ `{ skipPolicy: true }` เข้า engine —
เพราะ flag ที่ข้ามกติกาได้ คือช่องให้ข้ามจริงในวันที่รีบ

ทางที่เลือก: แยกเป็นสองฟังก์ชันตามหน้าที่
- `buildPostingDraft()` — สร้างบรรทัด + ตรวจโครงสร้าง (สมดุล, เงินสดผูกบัญชี,
  ข้อมูลครบตามหมวด, ผู้ถือถือทรัพย์ได้จริง, บัญชีตรงกับผู้ถือ)
- `buildPosting()` — เรียก draft แล้วบังคับกติกาเอกสารของ **ทุกผู้ถือที่รายการแตะ**

ผลพลอยได้ที่ดีกว่าเดิม: เดิมต้องจำไปเรียก `assertOwnerPolicy(input, targetOwner)`
เพิ่มเองในสาขาโอนข้ามผู้ถือ ตอนนี้ไล่จาก `result.transactions` ที่สร้างได้จริง
สาขาใหม่ในอนาคตจึงถูกตรวจอัตโนมัติโดยไม่ต้องจำ

เส้นทางที่บันทึกลงฐานข้อมูลต้องเรียก `buildPosting()` เท่านั้น —
ตอนนี้ `buildPostingDraft()` ถูกเรียกแค่ใน `preview.ts` กับเทสต์ และ DB trigger กันอีกชั้นอยู่แล้ว

### D-026 · ช่องจำนวนเงินของการขายทรัพย์ คำนวณให้ ไม่ให้พิมพ์

engine ปฏิเสธเมื่อสองค่านี้ไม่ตรงกัน ผู้ใช้จึงเจอ error ที่ไม่รู้ว่าต้องแก้ช่องไหน

ตอนนี้:

  (`RepaymentValue.amountPaid` ถูกลบทิ้ง)

### D-029 · เรื่องที่ยังค้าง — การตีราคาทรัพย์ (revaluation)
แผงขายทรัพย์มีช่อง "กำไรยังไม่รับรู้ที่เคยบันทึกไว้" และเตือนว่าต้องล้างออก
แต่ **ระบบยังไม่มีรายการตีราคาเลย** ไม่มีบัญชีส่วนเกินทุนจากการตีราคาในผังบัญชี
และไม่มีประเภทรายการสำหรับบันทึก ตัวเลข fair value ในงบดุลตอนนี้เป็น mock

จึงยังไม่ให้ engine ลงบรรทัดล้างกำไรยังไม่รับรู้ — ถ้าล้างสิ่งที่ไม่เคยลงไว้
งบจะเพี้ยนกว่าเดิม ข้อความในแผงแก้ให้ตรงความจริงแล้วว่าต้องทำด้วยรายการปรับปรุงแยก

ถ้าจะทำให้ครบ ต้องเพิ่มพร้อมกันสามอย่าง: บัญชี 3300 ส่วนเกินทุนจากการตีราคา ·
ประเภทรายการ "ปรับปรุง/ตีราคา" · และให้สาขา `capitalGain` ล้างยอดออกตอนขาย
**รอลูกพี่ตัดสินใจก่อนว่าจะตีราคาตามงวดไหน**

### D-030 · ปุ่มบันทึกต้องถาม engine ไม่ใช่เช็ครายการช่องที่ขาด
mace-windu จับได้ว่าปุ่ม "บันทึกเข้าสมุดบัญชี" ดูแค่ `missing[]` ซึ่งเป็นรายการช่องที่ฟอร์มรู้จัก
แปลว่า **นิติบุคคลที่ยังไม่แนบหลักฐาน กดบันทึกได้** — override กติกาที่ `corporate_strict` ห้าม override

ทางที่ **ไม่เลือก**: copy กติกานิติบุคคลไปเขียนไว้ใน `missing[]` ด้วย
เพราะนั่นคือกฎซ้ำสองที่อีกรอบ ซึ่งเป็นปัญหาเดียวกับ D-024

ทางที่เลือก: `useTxForm()` เรียก **`buildPosting()` ตัวจริง** ใน `useMemo`
ได้ `postingError` ออกมา แล้ว `canSubmit = missing.length === 0 && !postingError`

ผลคือทุกกติกาที่ engine บังคับ — รวมกติกาของ**ผู้ถือปลายทาง**ในรายการข้ามผู้ถือ
ซึ่งฟอร์มไม่มีทางรู้เอง — ถูกกั้นที่ปุ่มโดยอัตโนมัติ เพิ่มกฎใน engine ทีหลังก็ไม่ต้องแก้ฟอร์ม

### D-031 · ค้างรับ-ค้างจ่าย ลงลูกหนี้/เจ้าหนี้จริง ไม่ใช่ลงเงินสด

แก้โดยให้**ตารางกฎเป็นคนบอก**ว่าลูกหนี้/เจ้าหนี้ของแต่ละหมวดอยู่บรรทัดไหน (`accrualCoa`)
- ค่าเช่า / ค่าเช่าซื้อ → 1200 ลูกหนี้ค่าเช่า
- ดอกเบี้ยรับทั้งสามแบบ → 1210 ลูกหนี้ดอกเบี้ย
- ค่าใช้จ่ายทั้ง 16 หมวด → 2100 เจ้าหนี้การค้า-เจ้าหนี้อื่น

หมวดที่เหลือ **จงใจไม่ใส่** — ปันผลรับ ค่าคอมมิชชั่น เงินกินเปล่า การลงทุน การกู้ และการโอน
ยังไม่ได้ตัดสินใจว่าลูกหนี้ตัวนั้นควรอยู่บรรทัดไหน engine จะปฏิเสธพร้อมบอกเหตุ
ไม่ยัดลง "ลูกหนี้อื่น" ให้พ้นๆ ไป และฟอร์ม disable ช่องติ๊กให้เลย

ตอนตั้งค้าง `cfCategory` เป็น `none` ทั้งรายการ เพราะเงินยังไม่เคลื่อน

### D-032 · ตั้งค้างได้ต้องล้างได้ — เพิ่มสองหมวดที่หายไป
พอเปิดให้ตั้งค้างรับ ก็พบว่าตารางกฎมี `fin.pay_payable` สำหรับล้าง**เจ้าหนี้**

ลูกหนี้ค้างในงบดุลตลอดไป และผู้ใช้จะลงรายได้ซ้ำตอนเงินเข้าจริง

มีเทสต์กันไว้แล้วสามชั้น: ทุกบัญชีค้างต้องมีหมวดล้าง · หมวดล้างต้องไม่แตะ P&L ซ้ำ ·
บัญชีค้างต้องเป็นสินทรัพย์หรือหนี้สินเท่านั้น

### D-034 · อัปเกรด Next.js 15.1.7 → 15.5.25 (กลับคำตัดสินใจเดิม)
**ตอนแรกตัดสินใจว่าไม่อัปคืนนี้** เพราะเป็นความเสี่ยงที่ไม่จำเป็น — แอปยังเป็น mock
ไม่มีข้อมูลจริง และลูกพี่จะมาดูเช้านี้ ถ้าอัปแล้วพังตอนตีสามจะไม่มีอะไรให้ดู

**แล้วอ่าน error ของ Vercel ได้ ก็พบว่าคิดผิด**

```
errorCode:    VULNERABLE_NEXTJS_VERSION
errorMessage: Vulnerable version of Next.js detected, please update immediately.
errorStep:    direct:build
```

Vercel **ปฏิเสธที่จะ build** ให้เลย (CVE-2025-66478) — ไม่ใช่ build แล้วพัง
แปลว่าการ "ไม่อัปเพื่อความปลอดภัย" ไม่ได้ปลอดภัยกว่า มันแค่ทำให้ไม่มี deploy เลย
และสิ่งที่บล็อกอยู่ก็คือช่องโหว่ที่จดไว้เองในข้อนี้

อัปเป็น **15.5.25** (dist-tag `backport` = สายแก้ความปลอดภัยของ 15.x)
ไม่ข้ามไป 16 เพราะเป็น major ที่เสี่ยงกว่ามาก และ 15.5.25 แก้ CVE ตัวที่บล็อกอยู่แล้ว

ตรวจหลังอัป: typecheck · lint · 146 tests · build สะอาด 15 หน้า ·
ทุก route ตอบ 200 · รัน browser flow ทั้ง 6 ชุดซ้ำ (ขายทรัพย์กำไร/ขาดทุน · คืนเงินกู้ ·
โอนภายใน/ข้ามผู้ถือ · ปุ่มกั้นนิติบุคคล · ค้างรับ · ธงค้างตกค้าง) ผลเหมือนเดิมทุกตัว ไม่มี error ใน console

`npm audit` เหลือ 2 รายการที่เป็น **postcss ที่ Next bundle มา** ซึ่งเป็นเครื่องมือตอน build
ไม่ใช่ช่องโหว่ของแอปตอนรัน ช่องโหว่ตรงของ Next (RCE, auth bypass) หายหมดแล้ว
จะหายครบต้องไป Next 16 — เก็บไว้ทำตอนลูกพี่อยู่ ไม่ใช่เรื่องเร่งด่วนแล้ว

### D-035 · ระบุ Node floor เป็น `>=20` (เดิมเดาผิดว่า pin 22.x)
ตอนยังอ่าน build log ไม่ได้ ผมเดาว่า Vercel พังเพราะใช้ **Node 24** ส่วนที่นี่ใช้ 22
เลย pin `engines.node: "22.x"` ลง package.json

**เดาผิด** — สาเหตุจริงคือ Next.js ที่มีช่องโหว่ (D-034) และพอแก้แล้ว
Vercel **build ผ่านบน Node 24.x** ซึ่งพิสูจน์ว่าโปรเจกต์ไม่ได้ต้องการ 22 เลย

การ pin ไว้ที่ 22.x จึงเป็นการประกาศข้อจำกัดที่ไม่จริง แก้เป็น `>=20`
ซึ่งเป็นข้อกำหนดจริงของ Next 15.5 (`^18.18.0 || ^19.8.0 || >= 20.0.0`)
และยืนยันด้วยของจริงแล้วว่าใช้ได้ทั้ง 22 (เครื่อง dev) และ 24 (Vercel)

ไม่ไปแก้ค่า Node version ในหน้า settings ของ Vercel เพราะ build เขียวอยู่แล้ว
อย่าไปยุ่งกับสิ่งที่เพิ่งทำงานได้

**บทเรียน**: มีข้อมูลจริงให้ขุด (`get_deployment` คืน `errorCode` มาให้)
แต่ผมเดาก่อนแล้วค่อยขุด ควรสลับลำดับ

### D-036 · `cfCategory: "none"` แบกสองความหมาย — ต้องแยกตอนทำรายงาน CF
ตอนนี้ `none` ใช้กับสองเรื่องที่ไม่เหมือนกัน:
1. **โอนภายใน** — เงินเคลื่อนจริงแต่ไม่ต้องนับ เพราะย้ายกระเป๋า และต้อง**ตัดออกจากงบรวม**
2. **ค้างรับ-ค้างจ่าย** — เงินยังไม่เคลื่อนเลย **ห้ามตัดออกจากงบรวม** เพราะรายการนี้จริง

ตอนเขียนรายงานกระแสเงินสด ห้ามเอาสองอย่างนี้ไปรวมกลุ่มเดียวกัน
และถ้าทำ CF ทางอ้อม ต้องบวก/ลบ **Δลูกหนี้ − Δเจ้าหนี้** เข้าไปในกระแสเงินสดจากการดำเนินงาน
ไม่งั้นกำไรกับเงินสดจะไม่มีวันกระทบยอดกัน

ยังไม่แยก enum ตอนนี้เพราะยังไม่มีหน้ารายงาน CF ที่อ่านค่านี้จริง
แต่จดไว้เพื่อไม่ให้พลาดตอนทำ

### D-037 · engine อ่านธงจากตารางกฎ ไม่ใช่รหัสหมวด
`buildPosting()` เดิมเช็ค `sub.code === "trf.internal"` ตรงๆ ขณะที่ฟอร์มเช็ค `requires("transferTarget")`
ถ้าวันหนึ่งเพิ่มหมวดโอนตัวที่สอง (เช่น โอนเงินสดในมือเข้าธนาคาร) มันจะตกไปเส้นทางปกติ
ซึ่งเดบิตและเครดิต**บัญชีเงินสดเดียวกัน** ได้รายการว่างที่สมดุล ผ่านทุก Money Invariant
แล้วบัญชีปลายทางถูกทิ้งเงียบๆ — เงินหายไปจากระบบโดยไม่มีอะไรฟ้อง

ตอนนี้ทั้งสองฝั่งอ่านธงเดียวกันจากตารางกฎ
