### D-011 · พิสูจน์แล้วว่า Money Invariants กันได้จริงที่ระดับ DB
ไม่ได้เชื่อว่าเขียน trigger แล้วจะทำงาน — ลองละเมิดจริงทีละข้อ

| ทดสอบ | ผล |
|---|---|
| รายการไม่สมดุล (Dr 12,000 / Cr 9,999) | ✅ ถูกปฏิเสธ + rollback ทั้งชุด |
| บรรทัดเงินสดไม่ผูกบัญชีธนาคาร | ✅ ถูกปฏิเสธ |
| รายการที่ถูกต้อง | ✅ บันทึกได้ตามปกติ |
| ลบรายการที่บันทึกแล้ว | ✅ ถูกปฏิเสธ ให้ใช้ reverse |
| Corporate ไม่แนบหลักฐาน | ✅ ถูกปฏิเสธ |
| Corporate แนบหลักฐานแล้ว | ✅ บันทึกได้ |

**หมายเหตุทางเทคนิค**: trigger ตรวจสมดุลเป็น `deferrable initially deferred`
คือ fire ตอน **COMMIT** ไม่ใช่ตอน INSERT — จำเป็น เพราะระหว่างใส่บรรทัดแรก
รายการยังไม่สมดุลโดยธรรมชาติ ผลคือ application จะรู้ว่าผิดตอน commit
ซึ่งถูกต้องแล้ว (ทั้งรายการเข้าหรือไม่เข้าเลย ไม่มีครึ่งๆ กลางๆ)

การทดสอบรอบแรกรายงานผิดว่าข้อ 1 ไม่ผ่าน เพราะสคริปต์ลบข้อมูลทิ้งก่อน commit
จึงไม่ทัน trigger — ทดสอบซ้ำแบบปล่อยให้ commit จริงแล้วยืนยันว่ากันได้

### D-021 · เรียก mace-windu ตรวจจริงตามกติกาข้อ 7 — **BLOCK สองรอบ**
นี่คือครั้งแรกที่ใช้สภาเจไดจริง ไม่ใช่แค่มีไฟล์ และมันจับของได้

**รอบแรก — 8 ข้อ (7 ข้อถูกต้อง)**

ที่ร้ายที่สุดสองข้อ ทั้งคู่เป็น**การลงบัญชีผิดแบบเงียบๆ**:
- เลือกหมวด "คืนเงินกู้" แต่ไม่กรอกการแยกเงินต้น/ดอกเบี้ย → โค้ดตกไปเส้นทางปกติ
  ลงเงินต้นเต็มจำนวน **ดอกเบี้ยหายจาก P&L และหนี้สินลดเกินจริง**
- ขายทรัพย์โดยไม่กรอกต้นทุน → ตัดทรัพย์ด้วย**ราคาขาย**แทนต้นทุน ไม่รับรู้กำไรเลย

อีกข้อที่มีผลจริง: hard-code 4300/5900/5400 ไว้ใน engine ทำให้**กำไรจากการขายหลักทรัพย์
ไปโผล่บรรทัด "กำไรจากการขายทรัพย์"** ซึ่งหมายถึงอสังหาฯ — ย้ายเข้าตารางกฎเป็น
`gainCoa` / `lossCoa` / `interestCoa` แล้วแยก `inv.sell_securities` ไปใช้ 4900

ข้อที่ไม่ทำตาม: เสนอให้ใส่ `ownerId` ในบรรทัดบัญชี — แต่ `transaction_lines`
ไม่มีคอลัมน์นั้น owner อยู่ที่ระดับ transaction ตอบกลับไปแล้วและ mace-windu เห็นด้วย

**รอบสอง — 6 ข้อ (ทุกข้อถูกต้อง)**

ข้อที่ลึกที่สุดคือผลพวงจากคำตอบข้างบน: **ถ้า 1 transaction = 1 owner
แปลว่าโอนข้ามผู้ถือเป็นสองบรรทัดเงินสดในรายการเดียวไม่ได้** เพราะเงินสดของอีกฝ่าย
จะไปโผล่ในงบของฝ่ายแรก และ `intercompanyNature` เดิมอยู่แค่ใน summary ไม่ได้ลงบัญชีเลย
→ เคสปันผลจาก SRI ให้ธนากร **ไม่ลดส่วนของเจ้าของ** ผิดกฎที่เขียนไว้เองใน LEDGER_RULES

แก้เป็น: คืน **สอง transaction คู่กัน** ฝ่ายละหนึ่ง แต่ละอันสมดุลในตัวเอง
พร้อมคู่บัญชีตามลักษณะ — ปันผล: ฝ่ายจ่าย Dr 3200 (ลดส่วนของเจ้าของ) · ฝ่ายรับ Cr 4410 (รายได้)

อีกข้อที่สำคัญ: **อย่าเชื่อฟิลด์ที่ผู้ใช้เว้นได้** — เดิมดูว่าข้ามผู้ถือจาก
`transferToOwnerId` ที่เป็น optional ไม่ส่งมาก็ถือว่าโอนภายใน ทั้งที่บัญชีปลายทาง
เป็นของคนอื่น ตอนนี้อ่านจาก `BANKS` เอง

  `isBalanced` ทิ้ง · `posting.ts` เรียก `computeDisposal()` ต่อแทนคำนวณซ้ำ

- เทสต์ที่เคยยิงใส่ `disposalJournal()` ย้ายไปยิงผ่าน `buildPosting()` —
  ของเดิมพิสูจน์ฟังก์ชันที่ไม่มีใครเรียกจริง

### D-025 · แยก `buildPostingDraft()` ออกจาก `buildPosting()`
ปัญหา: พรีวิวต้องแสดงบรรทัดได้ตั้งแต่ยังไม่แนบไฟล์ แต่ `corporate_strict`
บังคับว่าต้องมีไฟล์หลักฐาน ถ้าใช้ฟังก์ชันเดียวกัน นิติบุคคลจะเห็นแต่
"ต้องแนบหลักฐาน" ไม่มีวันเห็นคู่บัญชีเลย

ทางที่ **ไม่เลือก**: ใส่ flag แบบ `{ skipPolicy: true }` เข้า engine —
เพราะ flag ที่ข้ามกติกาได้ คือช่องให้ข้ามจริงในวันที่รีบ

ทางที่เลือก: แยกเป็นสองฟังก์ชันตามหน้าที่
- `buildPostingDraft()` — สร้างบรรทัด + ตรวจโครงสร้าง (สมดุล, เงินสดผูกบัญชี,
  ข้อมูลครบตามหมวด, ผู้ถือถือทรัพย์ได้จริง, บัญชีตรงกับผู้ถือ)
- `buildPosting()` — เรียก draft แล้วบังคับกติกาเอกสารของ **ทุกผู้ถือที่รายการแตะ**

ผลพลอยได้ที่ดีกว่าเดิม: เดิมต้องจำไปเรียก `assertOwnerPolicy(input, targetOwner)`
เพิ่มเองในสาขาโอนข้ามผู้ถือ ตอนนี้ไล่จาก `result.transactions` ที่สร้างได้จริง
สาขาใหม่ในอนาคตจึงถูกตรวจอัตโนมัติโดยไม่ต้องจำ

เส้นทางที่บันทึกลงฐานข้อมูลต้องเรียก `buildPosting()` เท่านั้น —
ตอนนี้ `buildPostingDraft()` ถูกเรียกแค่ใน `preview.ts` กับเทสต์ และ DB trigger กันอีกชั้นอยู่แล้ว

### D-026 · ช่องจำนวนเงินของการขายทรัพย์ คำนวณให้ ไม่ให้พิมพ์

engine ปฏิเสธเมื่อสองค่านี้ไม่ตรงกัน ผู้ใช้จึงเจอ error ที่ไม่รู้ว่าต้องแก้ช่องไหน

  (`RepaymentValue.amountPaid` ถูกลบทิ้ง)

### D-029 · เรื่องที่ยังค้าง — การตีราคาทรัพย์ (revaluation)
แผงขายทรัพย์มีช่อง "กำไรยังไม่รับรู้ที่เคยบันทึกไว้" และเตือนว่าต้องล้างออก

งบจะเพี้ยนกว่าเดิม ข้อความในแผงแก้ให้ตรงความจริงแล้วว่าต้องทำด้วยรายการปรับปรุงแยก

ถ้าจะทำให้ครบ ต้องเพิ่มพร้อมกันสามอย่าง: บัญชี 3300 ส่วนเกินทุนจากการตีราคา ·
ประเภทรายการ "ปรับปรุง/ตีราคา" · และให้สาขา `capitalGain` ล้างยอดออกตอนขาย
**รอลูกพี่ตัดสินใจก่อนว่าจะตีราคาตามงวดไหน**

### D-030 · ปุ่มบันทึกต้องถาม engine ไม่ใช่เช็ครายการช่องที่ขาด
mace-windu จับได้ว่าปุ่ม "บันทึกเข้าสมุดบัญชี" ดูแค่ `missing[]` ซึ่งเป็นรายการช่องที่ฟอร์มรู้จัก
แปลว่า **นิติบุคคลที่ยังไม่แนบหลักฐาน กดบันทึกได้** — override กติกาที่ `corporate_strict` ห้าม override

ทางที่ **ไม่เลือก**: copy กติกานิติบุคคลไปเขียนไว้ใน `missing[]` ด้วย
เพราะนั่นคือกฎซ้ำสองที่อีกรอบ ซึ่งเป็นปัญหาเดียวกับ D-024

ทางที่เลือก: `useTxForm()` เรียก **`buildPosting()` ตัวจริง** ใน `useMemo`
ได้ `postingError` ออกมา แล้ว `canSubmit = missing.length === 0 && !postingError`

ผลคือทุกกติกาที่ engine บังคับ — รวมกติกาของ**ผู้ถือปลายทาง**ในรายการข้ามผู้ถือ
ซึ่งฟอร์มไม่มีทางรู้เอง — ถูกกั้นที่ปุ่มโดยอัตโนมัติ เพิ่มกฎใน engine ทีหลังก็ไม่ต้องแก้ฟอร์ม

### D-031 · ค้างรับ-ค้างจ่าย ลงลูกหนี้/เจ้าหนี้จริง ไม่ใช่ลงเงินสด

### D-036 · `cfCategory: "none"` แบกสองความหมาย — ต้องแยกตอนทำรายงาน CF

### D-038 · ต้นทุนหุ้น/กองทุนใช้ FIFO (ลูกพี่ตัดสิน 26/09)
เลือก FIFO ไม่ใช่ถัวเฉลี่ย

**ผลที่ตามมาทันทีกับการเก็บข้อมูล**: FIFO ต้องรู้ว่าล็อตไหนซื้อก่อน
จึงเก็บ "ต้นทุนเฉลี่ยต่อหน่วย" อย่างเดียวไม่ได้ — ต้องเก็บ**ทุกล็อต** (วันที่ซื้อ + จำนวน + ราคา)

ชีท 8 "พอร์ตลงทุน" ในเทมเพลตเดิมมีคอลัมน์ "ต้นทุนเฉลี่ยต่อหน่วย" ซึ่ง**ขัดกับ FIFO**
ถ้ากรอกแบบนั้นแล้วมาคิด FIFO ทีหลังจะทำไม่ได้เลย เพราะข้อมูลล็อตหายไปแล้ว
จึงเพิ่มชีท "พอร์ตลงทุน (รายล็อต)" ในไฟล์ยอดตั้งต้น ให้กรอกทีละล็อตแทน

ยังไม่เขียนตัวคำนวณ FIFO — `computeDisposal()` รับ `costBasis` เป็น input อยู่แล้ว
ตัวที่ต้องเพิ่มคือฟังก์ชันที่ตัดล็อตตามลำดับวันที่แล้วคืน costBasis ออกมา
ทำตอนต่อ DB เพราะต้องอ่านล็อตจากตาราง

ถ้า seed txn_types ที่ชี้ 5910 ก่อนเพิ่มบัญชี จะติด foreign key violation
และ**ขายขาดทุนจะ post ไม่ได้เลย**

แก้: migration `20260918000005` เพิ่มสองบัญชี แล้วย้าย seed ที่ generate ไปเป็น `...000006`
ให้เรียงหลัง (ลบ `...000004` ที่เป็นไฟล์ generate และถูกแทนที่ทั้งไฟล์ทิ้ง)
apply ขึ้น Supabase จริงแล้ว ตรวจกลับมาว่า loss_coa_code เป็น 5910 ทั้งสองหมวด

**3. ตารางแยกเงินสดไม่มีแถวว่าง**
มีแต่บัญชีที่อยู่ในระบบแล้ว ถ้าลูกพี่มีบัญชีที่ยังไม่เคยลงทะเบียน จะไม่มีที่กรอก
แล้วจะยัดยอดรวมลงบรรทัด 1100 → **เงินสดที่ไม่ผูกบัญชีจริง** ซึ่ง Money Invariant 2 ห้าม
เพิ่มแถวว่าง 6 แถวต่อผู้ถือ พร้อมป้ายบอกว่ากรอกบัญชีใหม่ได้

**4. รายการระหว่างกันมีแต่ข้อความเตือน ไม่มีช่องตรวจ**
แต่ละชีทลงตัวได้ทั้งที่งบรวมไม่ลงตัว ถ้าฝ่ายหนึ่งบันทึกลูกหนี้ระหว่างกัน
แต่อีกฝ่ายไม่บันทึกเจ้าหนี้ (Money Invariant 6)
เพิ่มช่องตรวจ **รวม 1310 − รวม 2310 = 0** ในชีทรวม แดง/เขียวเห็นทันที

**ข้อที่ไม่ทำตามที่เสนอ**: เสนอให้ `effectOf()` อ่าน contra จาก `statements.ts`
แทน hard-code `code === "3200"` — แต่ไปอ่านโค้ดจริงแล้วพบว่าบรรทัดนั้นเป็น
`isContra ? side === "cr" : side === "cr"` — **สองฝั่งของ ternary เหมือนกันเป๊ะ**
`isContra` ไม่ได้ทำอะไรเลยตั้งแต่แรก และผลลัพธ์ถูกอยู่แล้ว
(เครดิตเพิ่มส่วนของเจ้าของ · 3200 เดบิตแล้วยอดถอนโต = ส่วนของเจ้าของลด พอดี)
จึงลบโค้ดตายที่ทำให้คนอ่านคิดว่ามีการจัดการ contra อยู่ ดีกว่าเพิ่ม coupling ที่ไม่เปลี่ยนพฤติกรรม

### D-053 · ช่องเงินอ่านเครื่องหมายลบของตัวเองไม่ออก
mace-windu จับได้หลังเปิดให้ส่วนต่างจากการตีราคาติดลบ (D-050) ว่า `parseAmount()`
ตัดทุกอักขระที่ไม่ใช่ `0-9 . -` ทิ้ง — ซึ่งทำลายเครื่องหมายลบ**ที่ระบบเองแสดงออกมา**

รันจริงยืนยัน:
```
"(300,000.00)"  →  +300000     ← money() แสดงติดลบเป็นวงเล็บ
"−300000"       →  +300000     ← หน้าจอใช้ U+2212 ไม่ใช่ยัติภังค์
"300000-"       →  0 เงียบๆ
```
ผู้ใช้ก๊อปตัวเลขจากหน้าจอตัวเองมาวาง แล้ว**ตีราคาลงกลายเป็นตีราคาขึ้น** ผิดทิศทั้งก้อน

แก้สองชั้น เพราะชั้นเดียวไม่พอ:
1. `parseAmountOrNull()` เข้าใจวงเล็บ · U+2212 · en/em dash · `฿` · comma
   และ **คืน `null` เมื่ออ่านไม่ออก** ไม่ใช่ 0 (ศูนย์ที่ผู้ใช้ไม่ได้ตั้งใจ แยกไม่ออกจากศูนย์จริง)
2. **เลิกให้พิมพ์เครื่องหมาย** — เปลี่ยนเป็นปุ่ม "ตีราคาขึ้น / ตีราคาลง" + ช่องจำนวนบวก
   เพราะแป้นตัวเลขบนมือถือ (`inputMode="decimal"`) ไม่มีปุ่มลบ ต่อให้ parser ถูกก็กรอกไม่ได้อยู่ดี

**บทเรียน**: เปิดให้ค่าติดลบได้ ต้องตามไปดูทุกจุดที่ค่านั้นเดินผ่าน
เทสต์ผ่านหมดเพราะเรียก `computeDisposal()` ตรงๆ ไม่ได้ผ่านฟอร์ม — บทเรียนข้อ 3 ซ้ำอีกรอบ

- สั่งคืนเงินกู้แล้วเงินยังไม่ออก = เรายังต้องจ่าย = **เจ้าหนี้**
  (หนี้สินรวมไม่เปลี่ยน แค่ย้ายจาก "เงินกู้" ไป "ที่ต้องจ่ายทันที" — งบดุลยังพูดความจริง)

เพิ่มบัญชีเดียว **`1220 ลูกหนี้อื่น (รอรับเงิน)`** แล้วเติม `accrualCoa` ให้ครบ:
เงินเข้าที่ไม่ใช่ค่าเช่า/ดอกเบี้ย → 1220 · เงินออกทั้งหมด → 2100 (มีอยู่แล้ว)

**บทเรียน**: ผมเสนอกลไกใหม่ทั้งที่กลไกเดิมพอ เพราะมองจากฝั่ง "หมวดนี้ไม่มี accrualCoa"
แทนที่จะถามว่า "รายการนี้ค้างอยู่ในสถานะอะไรกันแน่" — คำถามหลังตอบได้ด้วยบัญชีที่มีอยู่แล้ว

### D-069b · ระวังล้างลูกหนี้ซ้ำสองทาง
`inv.collect_rent` · `inv.collect_interest` · `fin.pay_payable` คือหมวดที่ตัวมันเอง
ล้างลูกหนี้/เจ้าหนี้อยู่แล้ว · พอการ check สร้างบรรทัดล้างอัตโนมัติ จะมีสองทางที่ล้าง
ตัวเดียวกันได้ → ลูกหนี้ติดลบ

จำกัดสามหมวดนี้ให้ใช้กับ**ลูกหนี้/เจ้าหนี้ที่มาจากยอดตั้งต้น**เท่านั้น (ไม่มีรายการต้นทาง
ให้ check) · ลูกหนี้ที่เกิดจากรายการในระบบต้องล้างผ่านการ check ทางเดียว

### D-070 · ค้างรอลูกพี่ตอบ — คนคีย์ที่ถือสลิปอยู่ ต้องให้คนอื่น check อีกไหม
ก · check ทุกรายการเสมอ (เข้มสุด แยกหน้าที่จริง แต่สองขั้นตอนทุกครั้ง)
ข · คนคีย์ติ๊ก "เงินเข้าแล้ว" พร้อมเลือกบัญชี = ยืนยันในตัว (เร็ว แต่ยืนยันตัวเอง)
ค · ฝั่งบริษัท check เสมอ ฝั่งบุคคลติ๊กเองได้ — **ผมแนะข้อนี้**

ข้อ ค ตรงกับ Entity Policy ที่ใช้อยู่แล้วทุกเรื่อง ไม่ต้องจำกฎใหม่
และฝั่งบริษัทคือฝั่งที่ต้องตอบผู้สอบบัญชีได้จริง

**ต้องตอบก่อนเริ่ม D-066 และ D-067** เพราะมันเปลี่ยนว่ารายการหนึ่งลงบัญชีอะไรบ้าง
ทำข้ออื่นก่อนแล้วค่อยเปลี่ยน = ต้องกลับมาแก้ข้อมูลที่ลงไปแล้ว

### D-071 · v1.0 = ทาง A (แกนการเงิน) แต่ต้องต่อเป็น B ได้โดยไม่รื้อ

**เงื่อนไขที่ลูกพี่ย้ำ: ต้องอัพเป็น B ได้และเพิ่มไปได้อีก** แปลว่าสิ่งที่ทำใน A

2. โมดูลแยกโฟลเดอร์ตามกฎเหล็กข้อ 4 อยู่แล้ว เพิ่มโมดูลไม่ต้องแตะ core ledger

### D-072 · ลำดับสิทธิ์ 4 ระดับ — Super Admin / Management / Manager / Staff
ลูกพี่ปรับ 06/10 จากเดิม 3 ระดับ (`management`/`manager`/`user`) ที่ขึ้น DB ไปแล้ว

เปลี่ยนจริง 4 ข้อ:
1. **เพิ่ม Super Admin** ซึ่งเดิมไม่มี
2. **Manager อนุมัติ Ledger ได้เอง** — เดิมอนุมัติไม่ได้เลย เท่ากับ User
   นี่คือการเปลี่ยนที่ใหญ่ที่สุด
3. **แยก "ยืนยันรับ-จ่ายเงิน" ออกจาก "อนุมัติ Ledger" เป็นคนละสิทธิ์** —
   ถูกและสำคัญ เพราะเป็นสองเรื่องคนละเรื่อง (รับรองว่ารายการถูก กับ รับรองว่าเงินเคลื่อนจริง)
   เข้ากันพอดีกับ D-068
4. `user` → `Staff`

**"ทำได้ทุกอย่าง" ของ Super Admin = ทุกการกระทำ ไม่ใช่การยกเว้นกฎเงิน**
ห้ามลบรายการที่ post แล้ว · เดบิต=เครดิต · บรรทัดเงินสดต้องผูกบัญชี ·
`corporate_strict` ต้องมีหลักฐาน — บังคับที่ DB trigger ใช้กับทุกคนเท่ากัน ไม่มีข้อยกเว้นตาม role
ถ้ามีบัญชีใดลบรายการที่ลงแล้วได้ ตัวเลขทั้งระบบก็เชื่อไม่ได้

**ลูกพี่ยืนยัน 06/10**: Manager อนุมัติ Ledger ได้เอง แต่**ยืนยันการรับ-จ่ายเงินไม่ได้
ต้องให้ Management** · Management ทำได้ทั้งหมด

| | Super Admin | Management | Manager | Staff |
|---|---|---|---|---|
| สร้างรายการ | ✓ | ✓ | ✓ | ✓ |
| อนุมัติ Ledger | ✓ | ✓ | ✓ | ✗ |
| **ยืนยันรับ-จ่ายเงิน (CF)** | ✓ | ✓ | **✗** | ✗ |
| ตั้งค่า · ผู้ใช้ · สิทธิ์ | ✓ | ✓ | ✗ | ✗ |
| Void/กลับรายการ · เปิดงวดที่ปิด | ✓ | ✓ | ✗ | ✗ |

**คำตอบนี้แก้ปัญหาการแยกหน้าที่พอดี** — เดิมถ้า Manager ทำครบสามขั้น (คีย์ → อนุมัติ →
ยืนยันเงิน) รายการของบริษัทจะเข้า Ledger โดยไม่มีคนที่สองเห็นเลย · พอกั้นที่ขั้นยืนยันเงิน
**ขั้นที่แตะเงินจริงมีคนที่สองเสมอ** ส่วนขั้นบันทึกภาระ/สิทธิ์ Manager เดินเองได้ ไม่ติดคอขวด
และไม่ต้องผูกกับ Entity Policy ให้ซับซ้อนเพิ่ม

**ข้อควรเตรียม**: การยืนยันเงินทั้งบ้านไหลมาที่ Management → หน้า "ยืนยันรับ-จ่าย"
ต้องกรองตามบัญชีธนาคารและยืนยันเป็นชุดได้ ไม่ใช่ทีละแถวอย่างเดียว

### D-073 · สิทธิ์ต้องอ่านจากตาราง ไม่ใช่ hard-code ชื่อ role
ตอนนี้ `fn_is_management()` ถูกเรียก **12 จุด** ใน `20260917000004_rls.sql`
เพิ่ม Super Admin = ต้องแก้ทั้ง 12 จุด · ย้ายสิทธิ์ข้ามระดับ = ต้องเขียน migration
และโมดูลของทาง B จะเพิ่มอีกหลายสิบจุด

เปลี่ยนเป็น:
```sql
roles            (key, label, rank_order)
permissions      (key, label, note)     -- ledger.approve · cash.confirm · txn.void ...
role_permissions (role_key, permission_key)
fn_can('ledger.approve')                -- แทน fn_is_management()
```

ลูกพี่บอกว่า *"สามารถเปลี่ยนทีหลังได้"* — แบบนี้เปลี่ยนได้จริงโดยไม่ต้องแก้โค้ด
และตรงกับที่ PLAN.md เคยวางไว้ว่าจะมีตาราง `role_permissions`

**ข้อห้าม**: ตาราง permission มีได้เฉพาะสิทธิ์ว่า "ใครกดอะไรได้"
**ห้ามมีคีย์ที่ปิดกฎเงิน** เช่น `invariant.skip` หรือ `evidence.waive` —
ไม่งั้นกฎที่บังคับไว้ที่ DB จะถูก override ผ่านหน้า Settings

**ทำก่อน A2 (login)** เพราะ A2 ต้องอ่านสิทธิ์อยู่แล้ว ทำทีหลัง = เขียนสองรอบ
