### 00:3x · งานชิ้นที่ 1 — mace-windu BLOCK และมันถูก

ผมตรวจเองแล้วยืนยันว่า BLOCK ถูก และหนักกว่าที่รายงานมา:

```
หมวดที่ล้างบัญชี 1220 ได้ : ไม่มีเลยสักหมวด
หมวดที่ล้างบัญชี 2100 ได้ : fin.pay_payable อย่างเดียว · cashflow = operating
หมวดที่เพิ่งเปิดให้ตั้งค้างได้แต่ cashflow ไม่ใช่ operating : 21 หมวด
```

**เสียสองแบบ**
1. **ตั้งค้างแล้วล้างไม่ได้** — 10 หมวดที่พักที่ 1220 (ขายทรัพย์ · รับไถ่ถอน · กู้เงินเข้า ·
   เพิ่มทุน) ยอดจะค้างในงบดุลตลอดไป = บทเรียนข้อ 7 ซ้ำรอยเดิมเป๊ะ
2. **ล้างได้แต่เงินไปโผล่ผิดหมวดในงบกระแสเงินสด** — ซื้อทรัพย์ 10 ล้านแบบยังไม่จ่าย
   พอจ่ายจริงจะไปอยู่ Operating −10M ทั้งที่ต้องเป็น Investing −10M
   และเงินปันผลจ่ายจะโผล่ใน Operating

**ทำไมเทสต์ 217 ตัวไม่จับ** — เทสต์ยืนยันว่า "มีหมวดล้างอย่างน้อยหนึ่งหมวด"
ไม่ได้ยืนยันว่า**ล้างแล้วเงินลงหมวดเดิมในงบกระแสเงินสด** และไม่มีเคสเดินสองขั้น
(ตั้งค้าง → ล้าง) แล้วรวม CF · เป็นเทสต์ที่ยืนยันสิ่งที่โค้ดทำ ไม่ใช่ยืนยันกฎ

**ทำไมถึงหลุดมาได้** — ก่อนหน้านี้มีแค่ 21 หมวด operating ที่ตั้งค้างได้
ซึ่ง cashflow บังเอิญตรงกับหมวดล้างพอดี พอเปิดให้ทุกหมวดตั้งค้างได้
ความบังเอิญนั้นหายไป **นี่คือ "เปิดกฎครึ่งเดียว" รอบที่สองในคืนเดียวกัน**

### ตัดสินใจเอง (D-087) — คงข้อมูลไว้ แต่ปิดการใช้งานจนกว่าจะล้างได้จริง

**ไม่ถอย commit** เพราะ `accrualCoa` ของทั้ง 53 หมวดเป็นข้อมูลที่ถูกต้อง
มันคือ "ถ้าตั้งค้างจะไปพักที่ไหน" ซึ่งกลไกยืนยันรับ-จ่าย (C6) ต้องใช้

หมวดจะตั้งค้างจากฟอร์มได้ ต่อเมื่อมีหมวดล้างที่ (ก) ลดยอดบัญชีพักจริง — ดูทิศ
(ข) อีกขาแตะเงินสด (ค) **cashflow ตรงกับหมวดต้นทาง**

## งานชิ้นที่ 2 · ตารางสิทธิ์ 4 ระดับ + `fn_can()`

### 02:xx · agent รายงานว่าเจอรูโหว่ 3 จุด — ผมตรวจแล้ว **ไม่จริง**

agent บอกว่า `user_owner_access` · `period_closes` · `cash_confirmations`
"ไม่มี RLS / มีแต่ policy อ่าน" ซึ่งถ้าจริงคือเรื่องใหญ่มาก

ผมถาม `pg_policies` บน project จริงแล้ว — **ทั้งสามตารางมี policy เขียนอยู่แล้ว**
และทั้ง 21 ตารางใน `sri_os` เปิด RLS ครบหมด

**ทำไม agent ถึงเห็นผิด** — มันสร้าง Postgres ในเครื่องแล้ว replay migration ทั้งสาย
แต่ migration เก่าสองไฟล์ replay ไม่ผ่าน (ตัวมันเองรายงานไว้เอง) พอสองไฟล์นั้นล้ม
ของที่มันสร้างก็หายไปจากสำเนา **แล้ว agent สรุปจากสำเนาที่พังว่าของจริงไม่มี**

> บทเรียน: **ตรวจความปลอดภัยต้องเทียบกับของจริง ไม่ใช่เทียบกับสำเนาที่สร้างเอง**
> โดยเฉพาะเมื่อรู้อยู่แล้วว่าสำเนานั้นสร้างไม่ครบ

### แต่พอตามเส้นนี้ไป เจอของจริงที่อันตรายกว่า

RLS policy ใน Postgres เป็น **permissive** และ **OR กัน** — ถ้าไม่ลบของเก่า
สิทธิ์ใหม่ที่แคบกว่าจะไม่มีผลเลย เพราะของเก่าที่กว้างกว่ายังปล่อยผ่าน

migration ใหม่ **ไม่ได้ drop ของเก่า 5 ตัว**:
`access_manage` · `period_write` · `period_read` · `confirmations_read` · `contact_links_all`

ตัวที่เสียหายชัดสุดคือ **`access_manage` บน `user_owner_access`** —
ของเก่ากั้นด้วย `fn_is_management()` ซึ่งถูกทำเป็น wrapper ของ `fn_can('owner.view_all')`
ซึ่ง **Management มี** แต่ดีไซน์ใหม่ตั้งใจให้เป็น `users.manage` ซึ่งมีแต่ Super Admin
→ **Management ยังแจกสิทธิ์ดูข้อมูลการเงินของทุกคนให้ใครก็ได้อยู่ดี** ข้อจำกัดใหม่ถูกยกเลิกเงียบๆ

และเทสต์ของ agent ผ่านทั้งที่ผิด เพราะ DB ในเครื่องไม่มี `access_manage` ให้ OR ด้วย —
**เทสต์ที่รันบนสำเนาที่พัง ยืนยันได้แค่ว่าโค้ดทำงานบนสำเนาที่พัง**

สั่งแก้แล้ว: drop ของเก่าให้ครบก่อน create ของใหม่ · เพิ่มเคส "Management ต้องเขียน
`user_owner_access` ไม่ได้" · และแก้คอมเมนต์ในไฟล์ที่เขียนตามสมมติฐานผิด

### 03:xx · แก้ drop policy เสร็จ — และเจอเรื่องที่ใหญ่กว่า

agent drop ของเก่าครบแล้ว + เพิ่ม **sweep** ท้ายไฟล์ที่ลบทุก policy ซึ่งไม่อยู่ใน allow-list
(เพราะ drop ตามชื่ออย่างเดียวไม่พอ ในเมื่อมันมองของจริงไม่เห็น) และพิสูจน์ว่าเทสต์จับได้จริง
ด้วยการปิด drop แล้วดูว่าเทสต์ล้ม — **ไม่ใช่แค่รันแล้วเขียว**

#### แต่พอตามต่อ เจอว่า DB จริงกับ migration ไม่ตรงกัน

policy สี่ตัวที่อยู่ใน DB จริง — `access_manage` · `period_write` · `period_read` ·
`contact_links_all` — **ไม่อยู่ใน migration ไฟล์ไหนเลย** ถูกใส่มือเข้าไป

รวมกับที่รู้อยู่แล้วว่า migration เก่าสองไฟล์ replay จาก DB เปล่าไม่ผ่าน แปลว่า:

> **ตอนนี้ไม่มีใครรู้แน่ว่า DB จริงกับ migration ต่างกันตรงไหนบ้าง**
> สร้างฐานข้อมูลใหม่จาก migration จะได้ของที่**ไม่เหมือน**ของจริง

กระทบสามเรื่อง: กู้คืนตอนมีปัญหา · ทำ staging ไว้ทดสอบ · และการตรวจว่าสิทธิ์ถูกจริงไหม
(ตรวจกับไฟล์ก็ไม่ตรง ตรวจกับของจริงก็ไม่มีอะไรยืนยันว่าของจริงถูก)

**ยังไม่แก้คืนนี้** — ไม่ใช่เพราะไม่สำคัญ แต่เพราะต้องทำแบบตั้งใจ:
dump สถานะจริงออกมา เทียบกับ migration ทีละตารางทีละ policy แล้วออก migration
ที่ทำให้สองฝั่งตรงกัน · เป็นงานที่ต้องให้ลูกพี่รู้ตัวก่อนว่ากำลังจะแตะของที่ใช้งานอยู่
จดไว้เป็นงานต้นๆ ของพรุ่งนี้
